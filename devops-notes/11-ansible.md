# Ansible: автоматизация настройки серверов

Конспект по Ansible: как он работает, чем отличается от CI, compose и bash-скриптов, из чего состоит плейбук и как его писать. Практика на реальном сервере: [10-vps-setup.md](10-vps-setup.md) (ручная настройка, которую плейбук повторяет) и папка `ansible/` в репозитории (`site.yml`).

## Что это и зачем

Ansible приводит сервер в нужное состояние по описанию в YAML-файле. Вместо того чтобы вручную выполнять десятки команд после каждого пересоздания VPS, ты один раз описываешь результат («пользователь `deploy` существует, UFW включён, Docker установлен») и запускаешь одну команду.

Главные свойства:

- **без агента:** на сервер ничего ставить не нужно, достаточно SSH и `python3` (в Ubuntu он есть);
- **описывает результат, а не действия:** «пакет должен быть установлен», а не «выполни `apt install`»;
- **идемпотентность:** повторный запуск ничего не ломает и ничего не меняет, если сервер уже в нужном состоянии;
- **YAML:** тот же формат, что у `docker-compose.yml` и workflow GitHub Actions.

## Как это работает

```
твой ПК (WSL)                                        сервер(а)
┌──────────────────────┐                      ┌──────────────────┐
│ ansible-playbook     │      SSH             │  python3         │
│   site.yml           │ ───────────────────> │  (временные      │
│ inventory.ini        │  1. копирует модуль  │   модули Ansible │
│ ansible.cfg          │  2. запускает его    │   запускаются    │
│                      │ <─────────────────── │   и удаляются)   │
│ читает результат     │  3. ok / changed /   └──────────────────┘
└──────────────────────┘     failed
```

1. Запускаешь `ansible-playbook` на своей машине (**control node**).
2. Ansible читает `inventory.ini` (где сервера) и `site.yml` (что делать).
3. По SSH заходит на каждый сервер (**managed node**) и выполняет задачи **по порядку, сверху вниз**.
4. Каждая задача проверяет текущее состояние и меняет сервер только если оно отличается от описанного.
5. В конце печатает итог (`PLAY RECAP`).

Так как Ansible сам ходит на серверы («push-модель»), его можно запускать откуда угодно: с ноутбука, из CI, с jump-хоста.

## Идемпотентность

Скрипт `apt install tmux` при каждом запуске выполняет команду. Задача Ansible `apt: name=tmux state=present` сначала проверяет, установлен ли пакет:

| Состояние сервера | Результат задачи |
|-------------------|------------------|
| пакета нет | `changed` (установил) |
| пакет уже стоит | `ok` (ничего не делал) |

Поэтому второй запуск плейбука на настроенном сервере даёт `changed=0`. Это и есть проверка качества плейбука: если задача **каждый раз** `changed`, она написана неидемпотентно (обычно это `shell` или `command`).

Статусы задач:

| Статус | Значение |
|--------|----------|
| `ok` | состояние уже было правильным, изменений нет |
| `changed` | сервер изменён |
| `failed` | ошибка, прогон на этом сервере остановится |
| `skipped` | не выполнялась (не сработало условие `when`) |
| `unreachable` | не удалось подключиться по SSH |

## Сравнение с другими инструментами

### Ansible и CI (GitHub Actions)

Оба описываются YAML и состоят из последовательности шагов, но решают разные задачи.

| | GitHub Actions | Ansible |
|---|---|---|
| Задача | автоматизировать сборку, тесты, публикацию | настроить и поддерживать состояние сервера |
| Где выполняется | на временной виртуалке (runner), которая удаляется | на **постоянном** сервере по SSH |
| Что запускает | событие (`push`, `pull_request`, `cron`) | ты вручную, либо CI |
| Состояние | чистый runner каждый раз | сервер сохраняет состояние между запусками |
| Сценарий | `workflow` -> `job` | `playbook` -> `play` |
| Шаг | `step` | `task` |
| Готовый блок | `uses: actions/checkout@v7` | модуль `ansible.builtin.apt` |
| Параметры блока | `with:` | параметры модуля под его именем |
| Условие | `if:` | `when:` |
| Повтор по списку | `strategy.matrix` | `loop:` |
| Переменные | `env:` | `vars:` |
| Подстановка | `${{ secrets.TOKEN }}` | `{{ deploy_user }}` |
| Секреты | Secrets репозитория | `ansible-vault` |
| Порядок | шаги сверху вниз, `needs:` между job | задачи сверху вниз |

Один и тот же смысл «вызови готовый блок с параметрами»:

```yaml
# GitHub Actions
- uses: docker/login-action@v4
  with:
    registry: ghcr.io
    username: ${{ github.actor }}

# Ansible
- name: Поставить tmux
  ansible.builtin.apt:        # какой модуль вызвать (как uses:)
    name: tmux                # параметры модуля (как with:)
    state: present
```

Вместе они дополняют друг друга: CI собирает образы и публикует их в GHCR, а Ansible (или CI, который вызывает Ansible) раскатывает их на сервер.

### Ansible и docker compose

Оба декларативные: описывают желаемое состояние, а не команды. Но объекты разные: compose описывает **контейнеры** (сервисы, сети, тома), а Ansible описывает **сервер** (пользователи, пакеты, файрвол, файлы, сервисы). Ansible ставит Docker и кладёт на сервер `docker-compose.yml`, а compose уже запускает приложение.

### Ansible и bash-скрипт

| | Bash-скрипт | Ansible |
|---|---|---|
| Повторный запуск | может сломать или задвоить | безопасен (идемпотентность) |
| Описывает | действия | результат |
| Проверка без изменений | нет | `--check --diff` |
| Несколько серверов | цикл вручную | группы в inventory |
| Ошибки | нужно проверять самому | задача падает с понятным сообщением |
| Читаемость | зависит от автора | единый формат |

### Ansible и Terraform

Terraform **создаёт инфраструктуру** (сам VPS, сети, DNS), Ansible **настраивает то, что внутри** (пользователи, Docker, приложение). В связке: Terraform поднимает сервер и отдаёт IP, Ansible настраивает его.

## Структура проекта

```
ansible/
├── ansible.cfg              # настройки (где inventory, пользователь, ключ)
├── inventory.ini            # список серверов (в .gitignore: там реальный IP)
├── inventory.ini.example    # шаблон без реального IP, коммитится
├── site.yml                 # плейбук
└── .gitignore
```

Команды запускаются **из этой папки**: `ansible.cfg` читается из текущей директории. Если папка лежит на диске Windows (`/mnt/c/...`) с открытыми правами, Ansible проигнорирует `ansible.cfg` ради безопасности, поэтому проект держим в файловой системе WSL (`~/projects/...`).

## Основные понятия

| Понятие | Что это |
|---------|---------|
| **control node** | машина, с которой запускаешь Ansible (твой WSL) |
| **managed node** | сервер, который настраивается |
| **inventory** | список серверов, их группы и переменные |
| **playbook** | YAML-файл со сценарием (один или несколько play) |
| **play** | «на каких серверах (`hosts`) выполнить какие задачи» |
| **task** | один шаг: вызов модуля с параметрами |
| **module** | готовая единица работы (`apt`, `user`, `copy`, `ufw`, `systemd`) |
| **collection** | набор модулей (`ansible.builtin`, `community.general`, `ansible.posix`) |
| **handler** | задача, которая выполняется по сигналу `notify` один раз в конце play |
| **role** | оформленный набор задач, файлов и переменных для повторного использования |
| **facts** | данные о сервере, собираемые в начале (ОС, версия, IP), например `ansible_facts['distribution_release']` |
| **vars** | переменные |
| **vault** | шифрование секретов |

Полное имя модуля состоит из коллекции и имени: `ansible.builtin.apt`, `community.general.ufw`. Такая запись (FQCN) однозначна и рекомендуется.

## Основы YAML

- отступы **только пробелами** (обычно по 2), табы запрещены;
- `-` в начале строки: элемент списка;
- `ключ: значение`: пара в словаре;
- значение, которое начинается с `{`, `[` или содержит `: `, берётся в **кавычки**;
- `true` и `false`: логические значения; `"80"` в кавычках: строка;
- `|` после ключа: многострочный текст «как есть».

```yaml
vars:                      # словарь
  deploy_user: deploy      # ключ: значение
  ports:                   # список
    - "80"
    - "443"
  banner: "{{ deploy_user }}"   # в кавычках, потому что начинается с {{
content: |                 # многострочный текст
  строка 1
  строка 2
```

## Анатомия плейбука

```yaml
---
- name: Настройка VPS            # play (подпись для вывода)
  hosts: vps                     # группа из inventory
  become: true                   # выполнять через sudo

  vars:                          # переменные
    deploy_user: deploy

  tasks:                         # задачи по порядку
    - name: Поставить tmux       # подпись задачи
      ansible.builtin.apt:       # модуль
        name: tmux               # параметры модуля
        state: present

  handlers:                      # выполняются в конце, если был notify
    - name: Reload sshd
      ansible.builtin.systemd:
        name: ssh
        state: reloaded
```

## Частые конструкции

**`become: true`:** выполнять через sudo. Можно на уровне play (для всех задач) или на одной задаче.

**`vars` и `{{ }}`:** подстановка переменных, в том числе в именах задач и путях.

**`loop` и `item`:** повтор задачи для каждого значения списка.

```yaml
- name: Открыть порты
  community.general.ufw:
    rule: allow
    port: "{{ item }}"
    proto: tcp
  loop: ["80", "443"]
```

**`when`:** выполнять задачу только при условии.

```yaml
- name: Обновить кэш apt после добавления репозитория
  ansible.builtin.apt:
    update_cache: true
  when: docker_repo.changed
```

**`register`:** сохранить результат задачи в переменную (`changed`, `stdout`, `rc` и другие поля).

**`notify` и `handlers`:** запуск действия только если задача что-то изменила, и один раз в конце play. Типичный случай: перечитать конфиг сервиса после правки файла.

**`validate`:** проверить файл **до** записи. Ошибка в `sudoers` или `sshd` может отрезать доступ, поэтому критичные конфиги проверяем (`visudo -cf %s`, `sshd -t -f %s`, где `%s` это временный файл).

**`append: true`** у модуля `user` при `groups`: добавить в группу, не стирая остальные. Без него список групп заменяется целиком.

## Как писать плейбук, если не знаешь модулей

1. Выпиши, что сделал бы **руками** (твои заметки по серверу подходят идеально).
2. Для каждого шага найди модуль:

| Руками | Модуль |
|--------|--------|
| `apt install tmux` | `ansible.builtin.apt` |
| `adduser deploy` | `ansible.builtin.user` |
| положить ключ в `authorized_keys` | `ansible.posix.authorized_key` |
| создать или записать файл | `ansible.builtin.copy` |
| `ufw allow 80/tcp` | `community.general.ufw` |
| `systemctl enable --now docker` | `ansible.builtin.systemd` |
| добавить apt-репозиторий | `ansible.builtin.deb822_repository` |

3. Параметры смотри в документации: `ansible-doc ansible.builtin.apt` в терминале или docs.ansible.com (у каждого модуля есть блок Examples, его можно копировать и менять).
4. Запасной вариант: `ansible.builtin.shell` выполняет команду как есть. Работает, но каждый запуск будет `changed`, поэтому для постоянных плейбуков лучше нормальный модуль.

## Запуск: шпаргалка

| Команда | Что делает |
|---------|------------|
| `ansible vps -m ping -u ubuntu` | проверить связь с группой `vps` (ответ `pong`) |
| `ansible-playbook site.yml --syntax-check` | проверить синтаксис, на сервер не ходит |
| `ansible-playbook site.yml --check --diff` | пробный прогон: показать, что изменилось бы |
| `ansible-playbook site.yml` | выполнить плейбук |
| `ansible-playbook site.yml -u ubuntu` | заходить под другим пользователем |
| `ansible-playbook site.yml -K` | спросить пароль sudo |
| `ansible-playbook site.yml -e deploy_user=admin` | переопределить переменную |
| `ansible-playbook site.yml -v` (до `-vvv`) | подробный вывод для отладки |
| `ansible-playbook site.yml --limit 1.2.3.4` | выполнить только на одном сервере из inventory |
| `ansible-doc ansible.builtin.apt` | справка по модулю |
| `ansible --version` | версия `ansible-core` и пути |
| `ansible-galaxy collection list` | установленные коллекции |

`--check` на **чистом** сервере упадёт на задачах, которые зависят от того, что предыдущая задача реально что-то создала (например, установка пакетов из только что добавленного репозитория). Пробный прогон полезен на уже настроенном сервере.

## Паттерн: первый прогон и повторные

Чистый облачный сервер пускает только пользователя `ubuntu`, а плейбук в конце закрывает вход под ним (`AllowUsers deploy`). Поэтому два режима:

| Когда | Команда | Под кем заходит |
|-------|---------|-----------------|
| новый чистый сервер, один раз | `ansible-playbook site.yml -u ubuntu` | `ubuntu` |
| все следующие запуски | `ansible-playbook site.yml` | `deploy` (из `remote_user` в `ansible.cfg`) |

Порядок задач важен: настройку SSH (закрытие `ubuntu`) ставим **последней**, а handler перечитывает конфиг в конце. Иначе следующие задачи потеряли бы доступ к серверу.

Приоритет параметров подключения (от слабого к сильному): значение в `ansible.cfg` < ключ командной строки `-u` < переменная `ansible_user` в inventory < `-e ansible_user=...`. Поэтому, если в inventory задан `ansible_user`, флаг `-u` ничего не изменит.

## Что использует `ansible/site.yml`

| Блок | Модули | Раздел заметки |
|------|--------|----------------|
| система | `apt` | 3 |
| пользователь `deploy` | `user`, `authorized_key`, `copy` (sudoers + `validate`) | 4 |
| файрвол | `ufw` (политики, правила, `loop`, включение) | 7 |
| Docker | `deb822_repository`, `apt`, `systemd`, `user` | 10 |
| SSH hardening | `copy` + `validate`, `notify`, handler `systemd` reload | 6 |

Идея `authorized_key` с `exclusive: true`: в файле остаётся только указанный ключ. Ключ берётся из **публичного файла на твоём ПК** (`lookup('file', ...)`), а не копируется из чужой учётной записи (на облачных образах у `root` в `authorized_keys` стоит принудительная команда, и копия ломает вход).

## Секреты: `ansible-vault`

Токен GHCR и пароли нельзя хранить в плейбуке открытым текстом. Vault шифрует файл с переменными:

```bash
ansible-vault create secrets.yml                    # создать зашифрованный файл
ansible-vault edit secrets.yml                      # править
ansible-playbook site.yml --ask-vault-pass          # запуск с вводом пароля от vault
```

В плейбуке подключается через `vars_files: [secrets.yml]`. В git можно коммитить зашифрованный `secrets.yml`, но не пароль от него.

## Каталог ошибок

| Симптом | Причина | Что делать |
|---------|---------|------------|
| `Host key verification failed` | сервер новый или пересоздан, отпечаток неизвестен | один раз зайти `ssh user@IP` и ответить `yes`; при смене отпечатка `ssh-keygen -R <IP>` |
| `Permission denied (publickey)` | не тот пользователь, ключа нет на сервере или `AllowUsers` не пускает | проверить `-u`, `ssh -v`, ключ в `authorized_keys` |
| `UNREACHABLE!` | неверный IP в inventory, сервер выключен, SSH закрыт файрволом | проверить `ssh` вручную |
| `Missing sudo password` | у пользователя sudo с паролем | `NOPASSWD` в `sudoers.d` или `-K` |
| `couldn't resolve module/action 'community.general.ufw'` | коллекция не установлена | `ansible-galaxy collection install community.general` (аналогично `ansible.posix`) |
| `mapping values are not allowed here`, ошибка парсинга YAML | неверные отступы или двоеточие в значении без кавычек | `--syntax-check`, проверить отступы и кавычки |
| ошибка шаблона на `{{ ... }}` | значение начинается с `{{` без кавычек | взять значение в кавычки |
| задача каждый раз `changed` | неидемпотентная команда (`shell`, `command`) | заменить модулем или добавить `creates:` / `changed_when:` |
| `-u` не меняет пользователя | `ansible_user` задан в inventory | убрать из inventory или передать `-e ansible_user=...` |
| `ansible.cfg` игнорируется | папка доступна на запись всем (диск Windows в WSL) | держать проект в `~/projects/` |
| `deb822_repository` не найден | старая версия `ansible-core` | нужна 2.15 или новее, поставить через `pipx install --include-deps ansible` |

## Что дальше

- прогнать плейбук на чистом VPS дважды и убедиться, что второй прогон даёт `changed=0`;
- добавить деплой проекта: папка, `docker-compose.yml`, `.env` из шаблона, вход в GHCR, запуск на нужном sha;
- вынести секреты в `ansible-vault`;
- оформить задачи в **роли** (`roles/`), когда плейбук разрастётся;
- вызывать плейбук из GitHub Actions для автоматического деплоя;
- Terraform: создание самого сервера, затем Ansible настраивает его.
