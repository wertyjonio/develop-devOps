# Вопросы для собеседований: Docker и CI

[← К оглавлению](README.md)

Краткие эталонные ответы. Учить не наизусть, а пересказывать своими словами, добавляя пример из своих проектов.

## Docker

**1. Контейнер и виртуальная машина: чем отличаются, что общего?** ВМ эмулирует железо через гипервизор и запускает **своё ядро ОС**: тяжёлая, стартует минуты, изоляция сильнее. Контейнер это изолированный процесс на **ядре хоста**: изоляция через namespaces (что процесс видит), лимиты через cgroups (сколько ресурсов может взять). Он весит мегабайты и стартует за секунды. Общее: оба изолируют приложения, запускаются из образа/шаблона, переносимы, имеют свою сеть и файловую систему. На Windows Linux-контейнеры работают в лёгкой Linux-ВМ (WSL2).

**2. Образ и контейнер. Что с данными после `docker rm`?** Образ это неизменяемый шаблон из слоёв только для чтения. Контейнер это запущенный экземпляр с тонким слоем для записи сверху. После `docker rm` слой удаляется вместе с данными. Чтобы данные пережили контейнер, их выносят в именованный том или bind mount (пример: том `redis-data` в Guestbook; `down` его сохраняет, `down -v` удаляет).

**3. Как работает кэш слоёв? Почему сначала копируют `package.json`?** Каждая инструкция это слой; если инструкция и её входные файлы не изменились, слой берётся из кэша. Если слой изменился, все последующие пересобираются. Код меняется часто, зависимости редко, поэтому сначала копируют файл зависимостей и ставят их, а исходники после: тяжёлый шаг установки остаётся в кэше. Это про скорость пересборки, а не про размер образа.

**4. `CMD` и `ENTRYPOINT`; зачем exec-форма?** `RUN` выполняется при сборке, `CMD` и `ENTRYPOINT` задают, что запускать при старте. `CMD` это команда по умолчанию, её можно заменить в `docker run`; `ENTRYPOINT` фиксирует программу, а переданное становится её аргументами. Exec-форма (`["python", "app.py"]`) делает приложение PID 1, и оно получает `SIGTERM` при `docker stop`. В shell-форме PID 1 это shell, сигнал не доходит, и контейнер убивается через 10 секунд (код 137).

**5. `EXPOSE` и `-p`; как контейнеры находят друг друга?** `EXPOSE` только документирует порт. `-p 8080:80` публикует: порт 8080 хоста перенаправляется на порт 80 контейнера. В Compose создаётся сеть со встроенным DNS, который превращает имя сервиса в IP, поэтому Nginx обращается к `http://api:3000`. Наружу публикуется только frontend, `api` и Redis доступны лишь внутри сети (у меня две сети, `edge` и `backend`, так что frontend не видит Redis).

**6. Почему одного `depends_on` мало?** Он ждёт только запуска контейнера, а не готовности сервиса: Postgres после старта ещё инициализируется, и приложение может упасть с `connection refused`. Добавляют `healthcheck` у базы (`pg_isready`) и в приложении `depends_on` с `condition: service_healthy`. Проверка: `docker compose ps` (статус `healthy`), `docker compose up -d --wait`, `docker inspect --format '{{json .State.Health}}' <контейнер>`.

**7. Контейнер упал или `unhealthy`. Что делаешь?** Смотрю статус и код выхода (`docker compose ps -a`), читаю логи (`docker compose logs <сервис>`). При `unhealthy` логи могут быть чистыми, а сломана сама проверка, поэтому читаю `docker inspect ... .State.Health` (поле `Output`). Дальше сверяю конфиг (`docker compose config`), переменные окружения, порты, адрес прослушивания (`0.0.0.0`), сеть и DNS (`getent hosts`), права на тома. При необходимости захожу внутрь (`docker compose exec <сервис> sh`) и воспроизвожу проблему вручную.

## CI и GitHub Actions

**8. CI и CD; Continuous Delivery и Continuous Deployment.** CI это автоматическая проверка каждого изменения (линт, сборка, тесты, сканирование), цель в быстрой обратной связи об ошибках. Continuous Delivery: каждая проверенная версия готова к выкатке, но выкат запускается человеком (кнопка, подтверждение). Continuous Deployment: после зелёных проверок выкат на прод происходит автоматически, без ручного шага.

**9. Из чего состоит workflow в GitHub Actions?** Workflow это YAML-файл в `.github/workflows/`. Event (`on:`) запускает его (`push`, `pull_request`, `schedule`, `workflow_dispatch`). Внутри jobs, каждый выполняется на своём runner (чистая виртуальная машина) и состоит из steps: `run:` (команда) или `uses:` (готовый action). Jobs идут **параллельно** по умолчанию; порядок задаётся через `needs:` (в моём пайплайне `image-scan` ждёт `lint-and-build`).

**10. Где хранить пароли и токены для CI?** В GitHub Secrets (`${{ secrets.NAME }}`), в логах они маскируются. В репозиторий их класть нельзя: Git хранит историю навсегда, и удаление файла не помогает. Если секрет утёк, его нужно **перевыпустить**. Защита: `.env` в `.gitignore`, шаблон `.env.example` с тестовыми значениями, `gitleaks` по всей истории, push protection.

**11. Что такое `GITHUB_TOKEN` и принцип минимальных прав?** Это токен, который GitHub автоматически создаёт на время запуска workflow. Его права ограничивают блоком `permissions`. Принцип: давать только необходимое. У меня на уровне workflow `contents: read`, а `packages: write` выдан только job публикации образов в GHCR.

**12. Пайплайн покраснел. С чего начинаешь?** Нахожу **первый красный шаг** (остальные красные часто следствие), читаю конец его лога. Типичные причины: опечатка в YAML или флаге, неверный тег action, пустой секрет, уязвимость в Trivy, упавший smoke-тест. Воспроизвожу локально теми же командами. Перезапуск (`Re-run failed jobs`) уместен только для сбоев инфраструктуры, а не как способ «починить».

**13. Что такое smoke-тест и чем отличается от юнит-теста? Зачем `--retry`?** Smoke-тест это быстрая проверка уже собранной и запущенной системы: поднимается ли она и работают ли ключевые функции (`/health`, запись и чтение через БД). Юнит-тест проверяет отдельную функцию изолированно, без окружения. `--retry` и `--retry-connrefused` нужны, потому что сервис стартует не мгновенно; `--max-time` не даёт одной попытке повиснуть.

**14. Новая версия сломана после деплоя. Как откатиться?** Образы публикуются с тегом из хэша коммита (`guestbook-api:<sha>`), поэтому на сервере достаточно поднять предыдущий тег. Заранее должно быть готово: в compose тег задан переменной (`image: ghcr.io/<owner>/guestbook-api:${TAG:-latest}`), известен предыдущий рабочий `sha`, старые образы остаются в реестре, миграции данных обратимы. Команда: `TAG=<prev-sha> docker compose pull && TAG=<prev-sha> docker compose up -d`. Ручное подтверждение в Environment `production` и smoke-тест после деплоя уменьшают риск.
