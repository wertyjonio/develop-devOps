## 📦 СТУПЕНЬ 1: Система контроля версий Git

Git устроен как трехступенчатая система: **Рабочая директория** (файлы на диске) ➡️ **Индекс / Staging Area** (зона подготовки файлов к отправке) ➡️ **Локальный коммит** (сохраненный слепок кода) ➡️ **Удаленный репозиторий** (GitHub / GitLab).

### Базовый рабочий цикл

*   `git status` — **Самая важная команда контроля**. Показывает состояние репозитория прямо сейчас.
    *   *Красные файлы (Untracked / Modified):* Изменения есть только у тебя на ПК.
    *   *Зеленые файлы (Staged):* Файлы добавлены в индекс и готовы зафиксироваться в коммит.
*   `git add .` — добавить **вообще все** новые, измененные и удаленные файлы в текущей папке в индекс.
*   `git add <имя_файла>` — **Точечное добавление**. Подготавливает к отправке строго один конкретный файл.
*   `git reset` — **Отмена подготовки**. Очищает текущий индекс. Файлы возвращаются в «красную» рабочую зону. Сами файлы на диске не изменяются.
*   `git commit -m "тип: описание изменений"` — зафиксировать все «зеленые» файлы из индекса в локальный коммит.
    *   *DevOps-стандарт (Conventional Commits):* `docs:` (конспекты/документация), `feat:` (новый скрипт/фича), `fix:` (исправление багов), `chore:` (наведение порядка).
*   `git push` — отправить все локальные коммиты на удаленный сервер (например, в ветку `main` на GitHub).

## 🐧 СТУПЕНЬ 2: Linux Basics & Автоматизация

### 1. Продвинутая навигация и аудит файлов

*   `pwd` — показать текущий абсолютный путь от корня системы (`/`).
*   `file <имя>` — определить реальный тип файла по сигнатуре (магическим байтам), а не по расширению.
*   `stat <имя>` — показать полную метаинформацию о файле: размер, владельца, права доступа, три главные даты.
*   `tree` — показать структуру текущей папки и всех вложений в виде дерева.
*   `find <где> -name "<маска>"` — мощный поиск файлов на диске.
    *   *Пример:* `find . -name "*.md"` — искать все Markdown-файлы в текущей папке и подпапках.
    *   *⚠️ Подводный камень:* Обязательно писать флаг `-name`. Если написать `find . "*.sh"`, утилита решит, что папка для поиска называется `*.sh`, и выдаст ошибку.
*   `locate <имя>` — мгновенный поиск файлов по всей системе через готовую базу данных. Требует обновления базы командой `updatedb` после создания новых файлов.
*   `ln <файл> <имя_ссылки>` — создание **жесткой ссылки** (hard link). Ведет на те же данные на диске. Если удалить оригинал, ссылка продолжит работать.
*   `ln -s <файл> <имя_ссылки>` — создание **символической ссылки** (soft/symbolic link). Аналог ярлыка в Windows. Если удалить оригинал, ссылка станет «битой».






### 2. Потоки данных и перенаправления

В Linux у любого процесса есть три стандартных потока ввода/вывода:
*   `0` (`stdin`) — стандартный ввод (клавиатура / входящий поток из пайпа).
*   `1` (`stdout`) — стандартный полезный вывод (экран).
*   `2` (`stderr`) — стандартный вывод ошибок (экран).

*   `>` — направить `stdout` в файл с **полной перезаписью** старого содержимого.
*   `>>` — направить `stdout` в файл, **дописывая** строки в конец.
*   `2>` — перенаправить исключительно поток ошибок `stderr` в файл.
    *   *Пример:* `cat non_existent.txt 2> errors.log`
*   `2>&1` — склеить поток ошибок (`2`) с полезным выводом (`1`).
    *   *Пример:* `ping -c 1 8.8.8.8 > /dev/null 2>&1` — отправляет и полезный вывод, и ошибки в «черную дыру» Linux (`/dev/null`).
*   `|` (Пайп / Конвейер) — передает `stdout` первой команды на `stdin` второй команды.







### 3. Переменные окружения

*   `env` — вывести список всех активных глобальных (системных) переменных текущей сессии.
*   `export VAR="value"` — превратить локальную переменную терминала в глобальную переменную окружения.
    *   *⚠️ Подводный камень:* Вокруг знака `=` **нельзя ставить пробелы** (`VAR = "val"` вызовет ошибку). Значок `$` ставится только при чтении переменной (`echo $VAR`), при создании он не нужен. Имена переменных чувствительны к регистру.
*   `$PATH` — критически важная переменная. Содержит список папок, разделенных двоеточием, в которых Linux ищет исполняемые файлы команд.
    *   *Временное добавление пути:* `export PATH="$PATH:/home/user/my_folder"` (обязательно сохранять старый `$PATH` через двоеточие!).
    *   *Добавление текущей папки (`.`):* `export PATH="$PATH:."` — позволяет запускать скрипты из текущей папки просто по имени: `script.sh`.
    *   *⚠️ Безопасность:* На реальных серверах хранить точку `.` в `$PATH` опасно, так как злоумышленник может подкинуть вредоносный исполняемый файл в рабочую папку.
*   `.bashrc` — скрытый конфигурационный файл в домашней директории пользователя. Выполняется **каждый раз при открытии нового окна терминала**. Сюда прописываются кастомные `export PATH` и алиасы для постоянной работы.
*   `.bash_profile` / `.profile` — выполняются **один раз** при первом входе (логине) пользователя в систему.








### 4. Комплексная работа с текстом (Текстовые пайплайны)

*   `grep [опции] "шаблон" <файл>` — поиск строк по тексту или регулярному выражению.
    *   `-i` — игнорировать регистр букв.
    *   `-v` — инвертировать поиск строк (показать строки, где текста **нет**). Например: убрать успешные логи `grep -v "200 OK"`.
    *   `-n` — вывести номера строк.
    *   `-E` — включить расширенные регулярные выражения. Символ `|` внутри шаблона означает логическое «ИЛИ» (`grep -E '404|500'`).
    *   `-L` (или `--files-without-match`) — выводит исключительно **имена файлов**, внутри которых заданный текст ни разу не встретился. Применяется для поиска файлов-исключений.
*   `sort` — сортировка строк по алфавиту. Флаг `-n` включает правильную сортировку чисел, флаг `-r` разворачивает сортировку в обратном порядке.
*   `uniq` — удаление **повторяющихся подряд** строк. Перед `uniq` всегда должна идти команда `sort`.
    *   `-c` — посчитать количество уникальных повторений каждой строки.
*   `cut` — вертикальное вырезание колонок текста. Флаг `-d` задает символ-разделитель, флаг `-f` указывает номер нужного столбца.
    *   *Пример отсечения знака %:* `cut -d '%' -f 1` (делит строку `45%` на части и берет первую).
*   `wc` (Word Count) — подсчет метрик текста. Флаг `-l` считает точное количество строк.
*   `xargs` — берет строки из пайпа и передает их в качестве аргументов команде, которая не умеет читать `stdin` напрямую. Флаг `-r` отменяет запуск следующей команды, если на вход ничего не пришло.
    *   *Пример:* `find . -name "*.log" | xargs -r rm`
*   `sed` — потоковый текстовый редактор. Используется для автозамены «на лету».
    *   *Пример:* `sed -i 's/old/new/g' file.txt` (флаг `-i` сохраняет изменения в файл).
*   `awk` — мощный процессор структурированного текста. Автоматически разбивает строки на столбцы `$1`, `$2`, `$3` по пробелам.
    *   *Пример анализа реального лога (Топ-3 IP со статусом 200):*
        `grep "200" access.log | awk '{print $1}' | sort | uniq -c | sort -nr | head -n 3`






### 5. Сетевое администрирование и пакетный менеджер

Управление службами и программами на сервере (выполняется через `sudo` от имени суперпользователя):

*   `sudo apt update` — обновить локальную «витрину» доступного ПО из репозиториев в интернете. Выполняется перед установкой любого софта.
*   `sudo apt install -y <пакет>` — установить программу на диск. Флаг `-y` автоматически одобряет установку.
    *   *Пример:* `sudo apt install -y openssh-server` (установка SSH-сервера для удаленного подключения).
*   `sudo service <служба> start` — запустить фоновый процесс (службу/демона) в памяти системы прямо сейчас.
    *   *Пример:* `sudo service ssh start` (начинает слушать порт 22).

## 7. Автоматизация: Bash-скриптинг

Каждый скрипт — это текстовый файл с расширением `.sh`, написанный строго построчно. Запускается через `bash script.sh`.

### Системные коды возврата (Exit Codes)

Каждая команда после работы возвращает число операционной системе. Переменная **`$?`** хранит статус *последней* выполненной команды:
*   `0` — Успех. Команда выполнена идеально.
*   `1` (и от 1 до 255) — Ошибка. Код используется роботами (CI/CD) для аварийной остановки деплоя.
*   Команда `exit 1` внутри скрипта немедленно прерывает его работу и возвращает системе статус аварии.

### Шаблон продвинутого скрипта (Переменные, Условия `if/else`, Циклы `for`)

```bash
#!/bin/bash    # Шебанг (Shebang) — указывает системе интерпретатор для выполнения

# 1. Проверка переменных окружения на пустоту (флаг -z)
if [ -z "$DB_PASSWORD" ]; then
    echo "[ERROR] Секретный пароль базы данных не задан в системе!"
    exit 1  # Аварийный останов
fi

# 2. Цикл for по строкам текстового файла
# Конструкция $(cat ...) считывает инвентарь серверов
for ip in $(cat servers.txt)
do
    echo "--- Сканирую сервер $ip ---"
    
    # Пингуем хост 1 пакетом. Склеиваем stdout и stderr (2>&1) 
    # и отправляем в «черную дыру» /dev/null, чтобы очистить экран.
    ping -c 1 $ip > /dev/null 2>&1
    
    # Проверяем код возврата утилиты ping
    # ⚠️ Важно: Внутри квадратных скобок пробелы ОБЯЗАТЕЛЬНЫ с обеих сторон!
    if [ $? -eq 0 ]; then
        echo "[OK] Сервер доступен. Отправляю конфигурацию..."
        scp nginx.conf wert@$ip:/tmp/
    else
        echo "[WARNING] Сервер $ip лежит или закрыт файрволом!"
    fi
done
```

### Важные операторы сравнения чисел в `if`:

*   `-eq` — равно (equal)
*   `-ne` — не равно (not equal)
*   `-gt` — больше (greater than)
*   `-lt` — меньше (less than)
*   `-ge` — больше или равно (greater or equal)

## 8. Права доступа (`chmod`)

*   У каждого объекта в Linux есть 3 категории доступа: **U**ser (Владелец), **G**roup (Группа владельца), **O**thers (Все остальные).
*   Базовые типы прав:
    *   `r` (read) — чтение содержимого.
    *   `w` (write) — изменение содержимого (удаление/запись).
    *   `x` (execute) — право на запуск файла как программы или скрипта.
*   `chmod +x script.sh` — добавить флаг исполняемости для владельца, после чего Bash позволит запускать скрипт напрямую через `./script.sh` (в терминале имя файла подсветится зеленым цветом).

## 9. Первичная настройка и защита сервера (Server Hardening)

Пошаговый алгоритм защиты нового сервера от сетевых атак сразу после развертывания («золотой чек-лист» DevOps):

1.  **Создание изолированного пользователя для повседневной работы:**
    `sudo adduser devops_jun` — создает нового изолированного юзера (работать под привилегированным `root` напрямую запрещено стандартами ИБ).
    `sudo usermod -aG sudo devops_jun` — добавляет пользователя в группу `sudo` для возможности контролируемого временного повышения прав. Каждое действие логируется в `/var/log/auth.log`.
2.  **Настройка беспарольного SSH-доступа по ключам:**
    `ssh-copy-id devops_jun@<IP_сервера>` — дописывает локальный публичный ключ ПК в файл `~/.ssh/authorized_keys` конкретного пользователя на сервере для входа без паролей.
3.  **Запечатывание конфигурации безопасности SSH-демона:**
    `sudo vim /etc/ssh/sshd_config` — внесение жестких запретов:
    *   `PasswordAuthentication no` — отключает вход по обычным паролям (защита от брутфорса ботами).
    *   `PermitRootLogin no` — запрещает сетевой вход под пользователем `root` напрямую.
    `sudo service ssh restart` — перезапуск службы в памяти для применения новых конфигураций.
4.  **Развертывание и активация межсетевого экрана (Файрвола):**
    `sudo apt update && sudo apt install -y ufw` — установка утилиты управления файрволом UFW.
    `sudo ufw allow 22/tcp` — **Критический шаг!** Добавление явного исключения для порта 22 (SSH). Если включить файрвол без этого правила, произойдет перманентная самоблокировка на сервере.
    `sudo ufw enable` — активация файрвола в боевой режим. Переводит закрытие всех остальных портов под «глухую стену».
    `sudo ufw status` — аудит активности сетевых правил.

## 10. Состояния процессов и сигналы управления (Траблшутинг)

Фундаментальные механизмы ядра Linux для контроля жизненного цикла программ и диагностики их поведения:

### 1. Базовые состояния процессов (Колонка STAT в `ps aux`)

*   `R` (Running / Runnable) — Процесс выполняется прямо сейчас или полностью готов к работе и ждет очереди к CPU.
*   `S` (Interruptible Sleep) — Управляемый сон. Процесс ожидает внешнего события (ввода пользователя, сетевого пакета или таймера). Это дефолтное состояние большинства программ.
*   `D` (Uninterruptible Sleep) — Глубокий сон. Процесс завис на операции ввода-вывода (I/O), ожидая ответа от жесткого диска или сетевой папки. Его невозможно прервать или убить через `kill -9`.
*   `T` (Stopped) — Процесс остановлен или поставлен на паузу пользователем (например, через `Ctrl + Z`).
*   `Z` (Zombie) — Процесс завершен, но его родитель еще не прочитал код возврата. Память освобождена, но запись в таблице PIDs сохраняется.

### 2. Основные модификаторы состояний (Дополнительные символы в STAT)

*   `<` — Процесс имеет высокий приоритет (забирает ресурсы у других).
*   `N` — Процесс имеет низкий приоритет (работает, только когда система свободна).
*   `s` — Лидер сессии (например, главный процесс вашей командной оболочки).
*   `l` — Многопоточный процесс (внутри него запущено несколько Thread'ов).
*   `+` — Процесс выполняется на переднем плане (foreground) в текущем терминале.

### 3. Критические сигналы управления (Используются в `kill <SIGNAL> <PID>`)

*   `SIGTERM (15)` — Вежливое завершение. Стандартный сигнал при вызове `kill`. Процесс плавно закрывает файлы, сохраняет сессии и завершает работу.
*   `SIGKILL (9)` — Принудительное уничтожение (`kill -9`). Сигнал обрабатывается самим ядром, которое мгновенно стирает процесс из RAM. Процесс не успевает сохранить данные (опасно для баз данных).
*   `SIGHUP (1)` — Перезапуск конфигурации. Заставляет системные демоны (например, Nginx) перечитать конфигурационные файлы на лету без полной остановки сервиса.
*   `SIGINT (2)` — Прерывание с клавиатуры. Посылается процессу на переднем плане при нажатии комбинации `Ctrl + C`.
*   `SIGSTOP (19)` — Мгновенная заморозка. Посылается при нажатии `Ctrl + Z`. Процесс полностью перестает использовать CPU, оставаясь в оперативной памяти.

## 11. Аудит, мониторинг и поиск аномалий

Практические команды для инспекции запущенных программ и выявления утечек ресурсов:

### 1. Детальный снимок всех процессов в системе

`ps aux` — выводит полный список процессов всех пользователей без привязки к терминалу.
*   **Критические метрики:** Колонка `RSS` показывает реальную физическую память (RAM) в килобайтах, занимаемую процессом прямо сейчас. Ориентироваться при авариях нужно строго на неё, а не на виртуальную память `VSZ`.

### 2. Поиск конкретного процесса в выводе

`ps aux | grep "[n]ginx"` — фильтрация списка процессов через конвейер. Обертывание первой буквы в квадратные скобки `[ ]` — регулярное выражение, которое заставляет утилиту `grep` проигнорировать саму себя в выводе.

### 3. Выявление «прожорливых» процессов (Топ по памяти)

`ps aux --sort=-%mem | head -n 6` — сортирует процессы по убыванию потребления оперативной памяти и выводит топ-5 нарушителей с заголовком таблицы. Помогает быстро найти виновника утечки ресурсов.

### 4. Анализ связей процессов (Поиск Сирот и Зомби)

`ps axjf` — строит иерархическое дерево процессов с отображением `PPID` (Parent Process ID — идентификатор родителя).
*   **Поиск зомби без ложных срабатываний:** `ps auwx | awk '$8 ~ /Z/'` — проверяет строго 8-ю колонку вывода (STAT) на наличие признака зомби.

## 12. Управление жизненным циклом служб (SystemD)

Архитектурный подход к превращению обычных скриптов в автоматизированные фоновые службы (демоны) с гарантией отказоустойчивости:

### 1. Создание конфигурации системной службы (Юнита)

`sudo vim /etc/systemd/system/my-app.service` — создание файла конфигурации службы в защищенной директории.

*   **Базовый шаблон безопасного юнита:**

```ini
[Unit]
Description=My DevOps App
After=network.target      # запуск строго после поднятия сети

[Service]
Type=simple
ExecStart=/home/wert/app.sh  # абсолютный путь к исполняемому файлу
Restart=always            # автореанимация: SystemD мгновенно перезапустит процесс при падении
User=wert                 # запуск от имени изолированного юзера (ИБ-стандарт)

[Install]
WantedBy=multi-user.target # необходимо для корректного автозапуска при старте ОС
```

### 2. Применение конфигурации и запуск службы

`sudo systemctl daemon-reload` — заставляет SystemD перечитать файлы в папке `/etc/systemd/system/` и увидеть новый или измененный юнит.
`sudo systemctl start my-app.service` — запускает службу (под капотом ядро делает системные вызовы `fork()` и `exec()`).
`sudo systemctl enable my-app.service` — добавляет службу в автозапуск при включении сервера.

### 3. Контроль состояния и чтение логов

`sudo systemctl status my-app.service` — аудит текущего состояния службы (показывает статус `active (running)`, выделенный `PID` и потребление ресурсов).
`journalctl -u my-app.service -f` — вызов централизованного сборщика логов. Флаг `-f` (follow) фиксирует терминал и выводит логи приложения в режиме реального времени.

### 4. Просмотр юнитов

`sudo systemctl list-unit-files --type=service` — показывает список всех сервисов.

## 14. Мониторинг ресурсов

### Пример скрипта для мониторинга ресурсов

```bash
#!/bin/bash

# monitor.sh - простой мониторинг системы

LOG_FILE="/var/log/monitor.log"
THRESHOLD_CPU=80
THRESHOLD_MEMORY=80
THRESHOLD_DISK=90

log_message() {
    echo "$(date '+%Y-%m-%d %H:%M:%S') - $1" >> "$LOG_FILE"
}

check_cpu() {
    CPU_USAGE=$(top -bn1 | grep "Cpu(s)" | awk '{print $2}' | awk -F'%' '{print $1}')
    if (( $(echo "$CPU_USAGE > $THRESHOLD_CPU" | bc -l) )); then
        log_message "WARNING: High CPU usage: ${CPU_USAGE}%"
        # Отправить алерт
        echo "High CPU usage: ${CPU_USAGE}%" | mail -s "CPU Alert" admin@company.com
    fi
}

check_memory() {
    MEMORY_USAGE=$(free | grep Mem | awk '{printf("%.1f", $3/$2 * 100.0)}')
    if (( $(echo "$MEMORY_USAGE > $THRESHOLD_MEMORY" | bc -l) )); then
        log_message "WARNING: High memory usage: ${MEMORY_USAGE}%"
    fi
}

check_disk() {
    df -h | grep -vE '^Filesystem|tmpfs|cdrom' | awk '{print $5 " " $1}' | while read output;
    do
        usage=$(echo $output | awk '{print $1}' | cut -d'%' -f1)
        partition=$(echo $output | awk '{print $2}')
        
        if [ $usage -ge $THRESHOLD_DISK ]; then
            log_message "WARNING: High disk usage on $partition: ${usage}%"
        fi
    done
}

# Основная логика
log_message "Starting system monitoring"
check_cpu
check_memory  
check_disk
log_message "Monitoring completed"
```

## 15. Важные практические знания

### 🖥️ 1. Работа с процессами и памятью

*   `ps aux | grep [m]alware` — Найти запущенный процесс, не выводя в терминал сам `grep`. Квадратные скобки вокруг первой буквы ломают совпадение для самого `grep`.
*   `lsof /var/log/app.log` — Узнать, какой именно процесс (его имя и PID) прямо сейчас открыл и заблокировал этот файл.
*   `lsof | grep deleted` — Найти файлы, которые уже удалены через `rm`, но всё еще занимают место на диске, потому что их процессы не закрылись.
*   `sudo cp /proc/PID/exe ~/recovered_file` — Восстановить (скопировать) удаленный бинарник запущенного процесса прямо из оперативной памяти.
*   `kill PID` — Безопасная, мягкая остановка процесса (сигнал 15 / `SIGTERM`). Дает ему время сохранить данные. Стандарт в DevOps.
*   `kill -9 PID` — Жесткое уничтожение процесса на уровне ядра (сигнал 9 / `SIGKILL`). Применяется, только если он намертво завис.

### 💽 2. Очистка диска и лимиты

*   `sudo truncate -s 0 /var/log/app.log` — Мгновенно обнулить (осушить) файл до 0 байт, не удаляя его и не ломая запущенную программу.
*   `echo -n "" | sudo tee /var/log/app.log` — Альтернативный способ обнуления файла через поток `tee`, обходящий ошибку прав доступа `Permission denied`.
*   `ulimit -n` — Показать максимальное количество файлов, которое текущий пользователь может открыть одновременно.

### 📝 3. Работа с текстами и конфигами

*   `grep -Ev "^#|^$" /etc/nginx/nginx.conf` — Вывести конфиг в чистом виде, полностью вырезав из него пустые строки (`^$`) и комментарии (`^#`).
*   `grep "404" access.log | awk '{print $1}' | sort | uniq -c | sort -nr` — Классический конвейер DevOps. Отбирает ошибки 404, вырезает первый столбец (IP), считает уникальные адреса и сортирует их от самых частых к редким.

### 🔍 4. Поиск, рекурсия и архивы

*   `sudo find /etc/ -type f \( -name "*.key" -o -name "*.txt" \) -mtime -2` — Найти в `/etc/` только файлы (`-type f`), измененные за последние 2 дня (`-mtime -2`), с расширением `.key` ИЛИ (`-o`) `.txt`.
*   **Флаг рекурсии (`-r` или `-R`)** — Автоматическое применение команды (например, `rm -rf`, `chmod -R`, `chown -R`) к целевой папке и всему её содержимому на любую глубину.
*   `sudo tar -czvf ~/backup.tar.gz /etc/nginx/` — Создать (`c`) сжатый через gzip (`z`) архив, выводя процесс на экран (`v`), в файл (`f`) по указанному пути.

### 🌐 5. Сеть и файловая система

*   `sudo tcpdump -i eth0 -n -c 10 ip` — Перехватить на сетевой карте `eth0` ровно 10 пакетов (`-c 10`), показывая только чистые IP-адреса (`-n`), игнорируя системный шум (`ip`).
*   `sudo mount /dev/loop0 /mnt/backup` — Временно примонтировать (подключить) диск к созданной папке, чтобы прочитать его содержимое.
*   `timeout 3 bash -c 'cat < /dev/null > /dev/tcp/google.com/80' && echo "Open" || echo "Closed"` — Проверить, открыт ли порт на удаленном сервере, силами одного только Bash (без использования `telnet` или `netcat`).

### 📊 6. Мониторинг ресурсов (дополнительно)

*   `du -sh /var/log/*` — Считает реальный вес файлов и папок внутри указанной директории (флаг `s` — сумма, `h` — human-readable). Позволяет быстро локализовать, какая именно папка «отожрала» место на диске.
*   `uptime` — Показывает, сколько времени сервер работает без перезагрузки, сколько пользователей залогинено и среднюю нагрузку (**Load Average** за 1, 5 и 15 минут). Если Load Average сильно превышает количество ядер процессора — сервер перегружен.
*   `htop` (или `top`) — Интерактивный диспетчер задач в реальном времени. Показывает загрузку каждого ядра CPU, RAM и список самых «прожорливых» процессов. Позволяет визуально оценить состояние сервера и прямо из интерфейса нажать `F9`, чтобы убить зависший процесс.
*   `ps auxf` — Выводит полный список всех процессов в системе в виде дерева (`f` — forest), показывая, какой процесс породил другой. Помогает найти «родителя» вредоносного или зависшего процесса, чтобы прибить всю ветку целиком.
*   `pgrep -l nginx` — Ищет процессы по их имени и выводит только их ID (PID) и название. Не нужно писать длинные конструкции вроде `ps aux | grep nginx`, утилита сразу выдает чистые PID.
*   `pkill nginx` (или `killall nginx`) — Принудительно завершает **все** процессы с указанным именем (массовое убийство процессов). Если веб-сервер расплодил 20 дочерних процессов и завис, эта команда закроет их все за один раз.
*   `strace -p PID` — Подключается к работающему процессу и выводит в консоль все системные вызовы, которые он делает к ядру в реальном времени. Тяжелая артиллерия дебага. Если приложение «зависло» и ничего не пишет в логи, `strace` покажет, на каком именно файле или сетевом запросе оно споткнулось.
*   `curl -I https://google.com` — Отправляет веб-запрос на сайт и возвращает **только заголовки ответа** (без скачивания самой страницы). Быстрая проверка доступности сайта и кода ответа (`200 OK`, `301 Redirect`, `502 Bad Gateway`).

### 🔎 7. Продвинутые примеры `find`

*   **По размеру:**
    `sudo find /var/ -type f -size +1G` — Ищет в папке `/var/` файлы строго крупнее 1 Гигабайта (`+1G`). Можно указывать `M` (Мегабайты) или `k` (Килобайты).
*   **По времени изменения:**
    `sudo find /etc/ -type f -mtime -3` — Ищет файлы, которые были изменены или созданы за последние 3 дня (`-mtime -3`). Полезно при поиске следов взлома.
*   **По правам доступа:**
    `sudo find /var/www/ -type f -perm 777` — Находит файлы, у которых выставлены опасные права `777` (разрешено всё и всем). Используется для аудита безопасности.
*   **С автоматическим действием (Удаление):**
    `sudo find /tmp/ -type f -name "*.tmp" -mtime +7 -delete` — Находит в папке `/tmp` все файлы с расширением `.tmp`, которые старше 7 дней (`+7`), и автоматически удаляет их (`-delete`).

## 16. Продвинутое администрирование: Автоматизация, Безопасность и cgroups

### 🧟 1. Процессы-зомби (Zombie Processes)

*   `ps aux | grep "Z"` — Найти процессы со статусом `Z` (Zombie). Это процессы, которые уже завершили работу, но родительский процесс не прочитал их код возврата через `wait()`.
*   `ps -o ppid= -p [ZOMBIE_PID]` — Узнать PID родительского процесса (PPID), который породил зомби. Сам зомби убить нельзя (он уже мертв), поэтому нужно «прибить» или перезапустить его зависшего родителя: `sudo kill -9 [PPID]`.

### ⏰ 2. Автоматизация задач (Cron)

*   `crontab -e` — Открыть редактор расписания текущего пользователя.
*   **Синтаксис:** `Минута Час ДеньМесяца Месяц ДеньНедели Команда`
    *   `0 3 * * * /bin/bash /script.sh` — запуск каждую ночь строго в 03:00.
    *   `*/15 * * * * /bin/bash /script.sh` — запуск каждые 15 минут.
*   `crontab -l` — Вывести список всех текущих запланированных задач пользователя на экран.
*   **Современная замена cron (SystemD Timer):**

```ini
[Unit]
Description=Runs My Monitor Service every 30 seconds

[Timer]
# Запустить первый раз через 10 секунд после включения сервера
OnBootSec=10sec
# Дальнейшая частота запуска: каждые 30 секунд с момента последнего выполнения
OnUnitActiveSec=30sec
# Указываем, какой именно сервис пинать (если имена совпадают, можно не писать, но лучше зафиксировать)
Unit=my-monitor.service

[Install]
# Таймер должен включаться автоматически при старте системы
WantedBy=timers.target
```

### 👥 3. Управление пользователями и правами Sudo

*   `sudo useradd -m -s /bin/bash devops` — Создать нового пользователя `devops` с автоматическим созданием домашней папки (`-m`) и оболочкой по умолчанию (`-s /bin/bash`).
*   `sudo usermod -aG sudo devops` — Добавить пользователя в группу администраторов. Флаг `-a` критически важен, чтобы не стереть пользователя из старых групп.
*   `sudo visudo` — Безопасное редактирование файла конфигурации прав `/etc/sudoers`. Для настройки sudo без пароля в конец файла пишется: `devops ALL=(ALL:ALL) NOPASSWD: ALL`.

### 🔑 4. Харденинг (Безопасность) SSH

*   `ssh-keygen -t ed25519 -C "key_label"` — Сгенерировать пару надежных SSH-ключей (приватный и публичный) на стороне клиента.
*   `ssh-copy-id -i ~/.ssh/id_ed25519.pub user@IP_SERVER` — Скопировать публичный ключ на удаленный сервер в файл `~/.ssh/authorized_keys`.
*   Изменения в `/etc/ssh/sshd_config` (с последующим `sudo systemctl restart sshd`):
    *   `PermitRootLogin no` — запретить опасный вход под рутом напрямую из интернета.
    *   `PasswordAuthentication no` — отключить вход по паролям. Теперь на сервер пустит строго тех, у кого есть SSH-ключ.

### 🧱 5. Базовый файрвол (UFW)

*   `sudo ufw allow 22/tcp` — Разрешить входящий трафик для SSH. **Обязательно делать перед включением файрвола**, иначе вас навсегда заблокирует на вашем собственном сервере.
*   `sudo ufw enable` — Включить файрвол и активировать правила защиты.
*   `sudo ufw status verbose` — Показать текущий статус и подробный список открытых/закрытых портов.

### 🎛️ 6. Ограничение ресурсов процессов (cgroups v2 в Systemd)

В современных дистрибутивах Linux лимиты на CPU и память для процессов прописываются прямо внутри `.service` файлов Systemd в секции `[Service]`:

*   `MemoryMax=500M` — жесткий лимит оперативной памяти. Если процесс начнет течь и превысит 500 МБ, ядро Linux мгновенно прибьет его (OOM Killer).
*   `CPUAccounting=true` + `CPUQuota=50%` — лимит процессора. Ограничивает процесс на использование максимум 50% мощности от одного ядра CPU.

## 17. Глубокий сетевой стек Linux: Утилиты, Маршруты и Виртуальные мосты (Bridge)

В современном Linux старый пакет утилит `net-tools` (команды `ifconfig`, `route`) считается устаревшим. Стандартом является мощный пакет **`iproute2`** (все команды начинаются с буквы `ip`).

### 🌐 1. Управление IP-адресами и интерфейсами (Команда `ip a`)

Физические сетевые карты (`eth0`, `ens33`) или виртуальные интерфейсы в Linux называются **линками (links)**.

*   `ip a` (или `ip address`) — Выводит список всех сетевых интерфейсов, их статус (`UP` или `DOWN`), MAC-адреса и назначенные им IP-адреса с масками подсетей. Быстрая проверка, получила ли сетевая карта IP-адрес от DHCP-сервера или облачного провайдера.
*   `sudo ip address add 192.168.1.50/24 dev eth0` — Вручную назначает сетевой карте `eth0` дополнительный IP-адрес `192.168.1.50` с маской подсети `/24` (255.255.255.0). Используется при миграции серверов или когда одному серверу нужно временно присвоить "плавающий" IP-адрес (VIP), на который переключится трафик в случае падения основного сервера.
*   `sudo ip link set dev eth0 up` / `down` — Включает (`up`) или программно выключает (`down`) сетевой интерфейс. Симуляция аварии. DevOps-инженеры "гасят" сетевую карту на одном из серверов, чтобы проверить, сработает ли система высокой доступности (High Availability) и переключится ли трафик на резервный сервер.

### 🗺️ 2. Маршрутизация и Шлюзы (Команда `ip route`)

Сервер не знает, где в интернете находится `google.com`. Он знает только одно: если пакет предназначен не для локальной сети, его нужно отправить на **Шлюз по умолчанию (Default Gateway)** — роутер, который сидит на границе сети.

*   `ip route show` (или `ip r`) — Выводит таблицу маршрутизации ядра Linux.
    *   **Пример вывода:** `default via 192.168.1.1 dev eth0`
    *   **Разбор вывода:** Строка означает: «Все пакеты во внешний мир (`default`) отправлять через (`via`) шлюз `192.168.1.1` с помощью сетевой карты `eth0`».
    *   **Применение в работе:** Главный инструмент при ошибке "Network is unreachable". Если в таблице нет строки `default`, сервер изолирован в своей локальной сети и не может выйти в интернет.
*   `sudo ip route add 10.10.0.0/16 via 192.168.1.254` — Добавляет статический маршрут. Говорит серверу: «Если хочешь отправить пакет в подсеть `10.10.0.0/16`, отправляй его не на стандартный роутер, а на специальный шлюз `192.168.1.254`». Настройка связности в офисах и облаках. Используется, когда базы данных живут в отдельной защищенной подсети, и доступ к ним идет через выделенный VPN-шлюз.







### 🌁 3. Виртуальные мосты (Команда `ip link add ... type bridge`)

**Сетевой мост (Bridge)** — это виртуальный коммутатор (свитч), созданный прямо внутри оперативной памяти Linux. Он работает точно так же, как физический железный свитч: объединяет несколько сетевых интерфейсов в одну локальную сеть.
#### Зачем это нужно в DevOps и Docker?

Когда ты запускаешь 10 контейнеров Docker, им всем нужны IP-адреса. Но у тебя на сервере всего одна физическая сетевая карта `eth0`. Docker создает в Linux виртуальный мост (по умолчанию он называется `docker0`), присваивает ему сеть (например, `172.17.0.1/16`) и "подключает" каждый контейнер виртуальным кабелем к этому мосту. Контейнеры начинают видеть друг друга через этот мост, а во внешний мир выходят через твою физическую карту с помощью NAT (трансляции адресов).

#### Как собрать мост «руками» в Linux (Физика процесса):

1.  **Создаем виртуальный мост:**

```bash
sudo ip link add br0 type bridge
```

*Мы создали виртуальный свитч с именем `br0`.*

2.  **Включаем его:**

```bash
sudo ip link set dev br0 up
```

3.  **Привязываем сетевую карту к мосту:**

```bash
sudo ip link set eth1 master br0
```

*Мы как будто воткнули патч-корд от сетевой карты `eth1` в наш виртуальный свитч `br0`. Теперь весь трафик, приходящий на `eth1`, управляется мостом.*

4.  **Посмотреть состояние мостов в системе:**

```bash
ip link show master br0
# Или через утилиту bridge (если установлена):
bridge link





```

### 🛠️ 4. Продвинутая диагностика сетевого уровня

*   `ping -c 4 8.8.8.8` — Отправляет 4 пакета ICMP Echo Request до узла. Проверка базовой доступности. Если IP пингуется, а `ping google.com` выдает ошибку — сеть работает, но сломан DNS (проблема в `/etc/resolv.conf`).
*   `traceroute -n google.com` (или современный `mtr google.com`) — Показывает всю цепочку роутеров (хопов), через которые проходит ваш пакет на пути к цели. Флаг `-n` отключает долгий поиск имен роутеров. Поиск места обрыва. Если пакеты "застревают" на 5-м хопе, DevOps видит конкретный IP-адрес роутера провайдера, на котором ломается трафик, и может составить тикет в техподдержку.
*   `ss -tlnp` — Показывает, какие порты на каких IP-адресах слушает сервер. Если твое приложение слушает `127.0.0.1:8080`, оно недоступно извне. Если слушает `0.0.0.0:8080` — открыто для всего мира. Если порта вообще нет в списке — приложение упало при запуске.
*   `(echo >/dev/tcp/127.0.0.1/PORT) 2>/dev/null && echo open || echo closed` — проверяет открыт ли порт без утилит ss, netcat и т.д.

## 19. Сетевой сниффер `tcpdump`: Зачем он нужен и как спасает продакшн

### ❓ Зачем он нужен (Какую проблему решает)

Представь ситуацию: твое приложение не может достучаться до базы данных. Логи приложения пишут абстрактную ошибку `Connection timeout`. Файрвол вроде настроен правильно, порты открыты. Ты зашел в тупик.

В этот момент ты запускаешь `tcpdump` на сервере базы данных и смотришь на входящий трафик:
*   **Сценарий А:** Пакеты от приложения вообще не долетают до сервера БД. Вывод: проблема на внешнем роутере или в сети провайдера.
*   **Сценарий Б:** Пакеты долетают, сервер БД на них отвечает, но ответы не возвращаются обратно к приложению. Вывод: сломан обратный маршрут (маршрутизация).

`tcpdump` убирает гадание и показывает **голые факты**: дошел ли пакет до сервера и что сервер на него ответил.

### 🛠️ Точечные примеры применения в DevOps-рутине

*   **Посмотреть, какие HTTP-запросы летят на твой веб-сервер прямо сейчас:**

```bash
sudo tcpdump -A -i eth0 port 80
```

*(Флаг `-A` выводит содержимое пакетов в виде обычного текста. Ты сможешь глазами увидеть заголовки запросов, которые шлют пользователи).*

*   **Понять, работает ли вообще DNS на сервере:**

```bash
sudo tcpdump -i any port 53
```

*(Порт 53 — это DNS. Ты увидишь, отправляет ли сервер запросы к DNS-резолверу и приходят ли ответы).*

*   **Проверить, идет ли трафик от конкретного проблемного сервера:**

```bash
sudo tcpdump -i eth0 src 192.168.1.100
```

*(Фильтр `src` заставит утилиту игнорировать весь шум в сети и показывать пакеты только от отправителя с этим IP).*

*   **Записать трафик в файл для анализа в графическом интерфейсе (Wireshark):**

```bash
sudo tcpdump -i eth0 -w dump.pcap
```

*(Флаг `-w` сохраняет сетевой лог. Этот файл `.pcap` DevOps-инженер может скачать на свой рабочий ноутбук и открыть в красивой программе Wireshark, чтобы детально изучить проблему).*

### Базовый стек Docker: Архитектура, Жизненный цикл и Проброс портов

#### Главная физика Docker (Отличие от Виртуальных Машин)
* **Виртуальная Машина (ВМ):** Полностью эмулирует чужое железо (процессор, память) и запускает внутри себя **своё собственное, тяжелое ядро ОС**. Долго запускается и потребляет много ресурсов хоста.
* **Контейнер Docker:** Это **не виртуальная машина**. Внутри контейнера **нет операционной системы и своего ядра**. Docker использует существующее ядро твоего хостового Линукса и просто запускает в нем изолированный процесс. Контейнер весит мегабайты и запускается за доли секунды.

---

#### Архитектура и Понятия
* **Docker Daemon (Докер-демон):** Фоновая системная служба (`dockerd`), которая работает от root. Она скачивает образы, создает сети и запускает контейнеры.
* **Docker Client (CLI):** Консольная утилита `docker`, через которую мы пишем команды. Она сама ничего не делает, а просто шлет REST-запросы демону через Unix-сокет.
* **Образ (Image):** Замороженный шаблон, слепок файловой системы приложения (чертеж / класс в ООП). Изменить его нельзя.
* **Контейнер (Container):** Живой, запущенный в памяти экземпляр этого образа (объект класса в ООП). Из одного образа можно поднять хоть 100 одинаковых контейнеров.

---






### Базовые команды Docker: Управление образами, контейнерами и сетями

#### 📦 1. Команды для работы с ОБРАЗАМИ (Images)

* `docker images`
  * **Для чего:** Показать список всех скачанных или собранных образов (шаблонов), которые прямо сейчас лежат на жестком диске твоего сервера, их размер и теги.
* `docker pull [ИМЯ_ОБРАЗА]`
  * **Для чего:** Просто скачать образ с Docker Hub к себе на сервер, **не запуская его**. Полезно для предварительной подготовки тяжелых баз данных.
* `docker rmi [IMAGE_ID]`
  * **Для чего:** Удалить старый или ненужный образ с диска сервера (rm image), чтобы освободить место. *Нюанс: образ нельзя удалить, если на его основе создан хотя бы один контейнер (даже остановленный).*
* `docker tag [СТАРЫЙ_ОБРАЗ] [НОВЫЙ_ОБРАЗ:ВЕРСИЯ]`
  * **Для чего:** Присвоить образу имя и версию (тег), например `my-script:v1.0`. Если версию не указать, Docker автоматически ставит тег `latest`.
* `docker history [IMAGE_ID]`
  * **Для чего:** Показать «историю болезни» образа — из каких слоев и каких команд в Dockerfile он был собран. Помогает понять, почему образ весит слишком много.
* `docker push [ИМЯ_ОБРАЗА]`
  * **Для чего:** Отправить твой собственный собранный образ в интернет на Docker Hub или приватный склад компании (Registry), чтобы его могли скачать другие инженеры.

---






#### 🏃 2. Команды для работы с КОНТЕЙНЕРАМИ (Containers)

* `docker run -d -p 8080:80 --name my-web nginx`
  * **Для чего:** Создать и запустить контейнер из образа. Разбор флагов: `-d` (в фоне), `-p` (проброс портов Хост:Контейнер), `--name` (кастомное имя).
* `docker ps`
  * **Для чего:** Вывести список **только запущенных** в данный момент процессов-контейнеров.
* `docker ps -a`
  * **Для чего:** Вывести вообще все контейнеры в системе (включая упавшие и остановленные).
* `docker stop [CONTAINER_ID/NAME]`
  * **Для чего:** Мягко остановить работающий контейнер (сигнал `SIGTERM`). Программа внутри корректно завершает работу, контейнер переходит в статус `Exited`.
* `docker rm [CONTAINER_ID/NAME]`
  * **Для чего:** Полностью удалить контейнер из системы. **Внимание:** файлы, которые были созданы внутри этого контейнера во время работы, сотрутся навсегда!
* `docker logs -f [CONTAINER_NAME]`
  * **Для чего:** Посмотреть, что пишет приложение внутри контейнера. Флаг `-f` включает живой live-поток логов.
* `docker exec -it [CONTAINER_NAME] bash`
  * **Для чего:** "Провалиться" внутрь изолированной файловой системы запущенного контейнера и запустить там терминал `bash`.

---

#### 🌐 3. Команды для работы с СЕТЯМИ (Networks)

* `docker network ls`
  * **Для чего:** Показать список всех виртуальных сетей, созданных внутри Docker. По умолчанию ты увидишь три сети: `bridge` (мост), `host` (прямая сеть сервера) и `none` (полная изоляция).
* `docker network create [ИМЯ_СЕТИ]`
  * **Для чего:** Создать свою собственную изолированную подсеть (виртуальный свитч). 
  * **DevOps-контекст:** Это лучшая практика безопасности. Ты создаешь сеть `my-secure-net` и запускаешь контейнеры базы данных и кода внутри неё. Они могут общаться друг с другом, но никто из внешнего мира до них не доберется.

### Типы сетей в Docker (Сетевая изоляция)

Когда вы запускаете контейнер, вы можете явно указать ему тип сети через флаг `--network [ТИП]`.

#### 1. Bridge (Мост) — Стандартный тип по умолчанию
*   **Как работает:** Docker создает виртуальный свитч внутри памяти хоста. Каждый контейнер получает свой скрытый внутренний IP-адрес (например, `172.17.0.2`). Напрямую из интернета до этих адресов не добраться. Чтобы открыть к ним доступ, нужно делать проброс портов через `-p 8080:80`.
*   **Зачем нужен:** Это основной рабочий режим. Используется для изоляции приложений. Если создать свою кастомную сеть (`docker network create`), контейнеры внутри нее смогут общаться друг с другом по своим именам благодаря встроенному DNS Docker.

#### 2. Host (Сеть хоста) — Полное слияние с сервером
*   **Как работает:** Контейнер полностью лишается сетевой изоляции. Он использует сетевой стек вашего реального Linux-сервера напрямую. Если приложение внутри контейнера слушает порт 80, этот порт мгновенно открывается на вашем реальном сервере. Флаг `-p` здесь не нужен и не работает.
*   **Зачем нужен:** Для максимальной скорости работы сети. Проброс портов в режиме `bridge` тратит ресурсы CPU на трансляцию адресов (NAT). Режим `host` используют для тяжелых баз данных или систем сбора логов, где важна каждая миллисекунда.

#### 3. None (Полная изоляция) — Сетевой вакуум
*   **Как работает:** Контейнер запускается вообще без сетевой карты. У него есть только интерфейс `lo` (localhost) для общения с самим собой. Сети и интернета внутри контейнера нет физически.
*   **Зачем нужен:** Для максимальной безопасности при обработке секретных данных. Например, вам нужно запустить скрипт, который генерирует криптографические ключи или проверяет пароли. В режиме `none` вы гарантированно застрахованы от того, что код случайно сольет данные в интернет.

---

#### 🌐 Продвинутые типы сетей (Коротко для собеседований)
*   **Overlay (Оверлейная сеть):** Нужна, когда у вас не один сервер, а **целый кластер из нескольких машин** (Docker Swarm или Kubernetes). Overlay связывает виртуальным туннелем контейнеры, запущенные на физически разных компьютерах, в одну общую локальную сеть.
*   **Macvlan:** Позволяет назначить контейнеру реальный, физический MAC-адрес. Для вашего домашнего или офисного роутера такой контейнер будет выглядеть как отдельный физический компьютер, подключенный проводом. Контейнер получит IP-адрес напрямую от вашего домашнего роутера (например, `192.168.1.150`).









### Написание Dockerfile: Директивы и Физика сборки образов

Dockerfile — это обычный текстовый файл (строго с большой буквы и без расширения), в котором построчно записаны команды для сборки нашего приложения. 

Каждая директива (FROM, RUN, COPY) создает новый неизменяемый слой на жестком диске.

#### 🧱 Базовые директивы сборки (Конструктор образа)

* FROM (База)
  * **Что делает:** Самая первая строчка любого Dockerfile. Указывает, какой готовый шаблон (образ) мы берем за основу.
  * *Пример:* `FROM python:3.10-slim` (берем чистый, облегченный шаблон со встроенным Python).

* RUN (Действие при сборке)
  * **What делает:** Выполняет стандартные команды Linux (как в терминале) **в момент сборки самого образа**.
  * *Пример:* `RUN apt-get update && apt-get install -y htop` (скачивает утилиту htop внутрь нашего будущего шаблона).

* COPY (Копирование файлов)
  * **Что делает:** Копирует файлы или папки с твоего реального компьютера (хоста) внутрь файловой системы образа.
  * *Пример:* `COPY ./my-script.py /app/` (переносит твой питоновский скрипт в папку /app/ внутри образа).

* ADD (Продвинутое копирование)
  * **Что делает:** Похож на COPY, но с суперспособностями. Умеет скачивать файлы по URL-ссылкам из интернета напрямую в образ, а также автоматически распаковывать архивы (`.tar.gz`, `.zip`) при копировании.
  * *DevOps-нюанс:* Если нужно просто скопировать локальные файлы, всегда используют чистый `COPY` — это безопаснее и быстрее.

* WORKDIR (Рабочая папка)
  * **Что делает:** Аналог команды `cd` в Linux. Задает текущую рабочую директорию для всех последующих команд.
  * *Пример:* `WORKDIR /app` (все следующие команды будут выполняться внутри папки `/app`).

* ENV (Глобальные переменные среды)
  * **Что делает:** Задает переменные окружения, которые будут доступны внутри контейнера всегда.
  * *Пример:* `ENV MONGO_DB_PORT=27017` или `ENV APP_ENV=production`.

* ARG (Переменные сборки)
  * **Что делает:** Задает временные переменные, которые нужны **только в момент сборки образа** (для подстановки версий пакетов), но внутри готового запущенного контейнера они исчезнут.

* EXPOSE (Документирование порта)
  * **Что делает:** Подсказка для других инженеров, какой сетевой порт приложение внутри контейнера слушает по умолчанию.
  * *Пример:* `EXPOSE 8080`. *Важно:* эта команда не открывает порт наружу автоматически, проброс портов всё равно нужно делать через флаг `-p` при запуске контейнера.

* USER (Безопасность / Харденинг)
  * **Что делает:** Переключает пользователя. По умолчанию все процессы в Docker запускаются от имени всемогущего `root`. Директива `USER devops` заставляет приложение работать из-под обычного пользователя, чтобы хакеры не получили контроль над всем сервером при взломе кода.

---

#### 🏁 Стартовые директивы запуска (Запуск контейнера)

Эти команды выполняются не при сборке, а **в момент старта контейнера** (когда ты пишешь `docker run`).

* CMD (Дефолтная команда запуска)
  * **Что делает:** Задает главную команду, которая включится при старте контейнера. **Её можно легко переписать снаружи** при запуске команды `docker run`.
  * *Пример:* `CMD ["python", "main.py"]`

* ENTRYPOINT (Жесткая точка входа)
  * **Что делает:** Намертво фиксирует исполняемый файл, который запустится при старте контейнера. Переписать её снаружи сложнее.
  * *Пример:* `ENTRYPOINT ["nginx", "-g", "daemon off;"]`
