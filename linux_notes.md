## 1. Git

Путь изменений: **рабочая директория** → **индекс (staging)** → **локальный коммит** → **удалённый репозиторий** (GitHub/GitLab).

- `git clone <url>` — скопировать репозиторий.
- `git status` — главная команда контроля.
  - Красные файлы (untracked / modified): изменения только на твоём ПК.
  - Зелёные файлы (staged): добавлены в индекс, готовы к коммиту.
- `git add .` — добавить в индекс все изменения в текущей папке.
- `git add <файл>` — добавить один файл.
- `git reset` — убрать всё из индекса. Файлы на диске не меняются.
- `git commit -m "тип: описание"` — зафиксировать индекс в коммит.
- `git push` / `git pull` — отправить / забрать коммиты.
- `git log --oneline` — краткая история, `git diff` — что изменилось.
- `git switch -c <ветка>` — создать ветку и перейти в неё.

**Conventional Commits:** `feat:` новая функциональность, `fix:` исправление, `docs:` документация, `chore:` наведение порядка.

**Важно:** секреты (`.env`, ключи, пароли) в репозиторий не коммитим, а добавляем в `.gitignore`. Если секрет попал в историю, удаления файла недостаточно: ключ нужно перевыпустить.

## 2. Файлы и навигация

### Просмотр и аудит
- `pwd` — текущий абсолютный путь.
- `ls -la` — список файлов, включая скрытые, с правами.
- `tree` — структура папки деревом.
- `file <имя>` — реальный тип файла по сигнатуре, а не по расширению.
- `stat <имя>` — размер, владелец, права, три даты.
- `du -sh /var/log/*` — вес папок и файлов (`-s` сумма, `-h` человекочитаемо). Помогает найти, что «съело» диск.
- `df -h` — свободное место по разделам.

### Поиск: `find` и `locate`
- `find <где> -name "<маска>"` — флаг `-name` обязателен: в `find . "*.sh"` маска будет принята за путь и вернётся ошибка.
- `locate <имя>` — мгновенный поиск по готовой базе. После создания новых файлов нужен `sudo updatedb`.

```bash
find . -name "*.md"                                           # по имени
sudo find /var/ -type f -size +1G                             # по размеру (M, k — мега/килобайты)
sudo find /etc/ -type f -mtime -3                             # изменены за 3 дня (следы взлома)
sudo find /var/www/ -type f -perm 777                         # опасные права (аудит)
sudo find /etc/ -type f \( -name "*.key" -o -name "*.txt" \) -mtime -2   # .key ИЛИ .txt
sudo find /tmp/ -type f -name "*.tmp" -mtime +7 -delete       # удалить старые временные
find . -name "*.log" | xargs -r rm                            # удалить найденное через xargs
```

### Ссылки
- `ln <файл> <ссылка>` — **жёсткая** ссылка: те же данные на диске. Оригинал удалён, ссылка работает. Не работает между разделами и для папок.
- `ln -s <файл> <ссылка>` — **символическая** (как ярлык в Windows). Оригинал удалён, ссылка «битая».

### Архивы, диски, очистка
- `sudo tar -czvf ~/backup.tar.gz /etc/nginx/` — создать (`c`) сжатый gzip (`z`) архив с выводом процесса (`v`) в файл (`f`). Распаковать: `tar -xzvf backup.tar.gz`.
- `sudo mount /dev/loop0 /mnt/backup` — примонтировать диск в папку.
- `sudo truncate -s 0 /var/log/app.log` — обнулить файл, не удаляя его и не ломая запущенную программу.
- `echo -n "" | sudo tee /var/log/app.log` — альтернатива, когда обычное перенаправление даёт `Permission denied`.
- `lsof /var/log/app.log` — какой процесс держит файл.
- `lsof | grep deleted` — файлы, удалённые через `rm`, но всё ещё занимающие место, потому что процесс их не закрыл. Лечится перезапуском процесса.
- `sudo cp /proc/<PID>/exe ~/recovered_file` — восстановить удалённый бинарник работающего процесса.
- Рекурсия: флаг `-r` / `-R` применяет команду (`chmod -R`, `chown -R`, `rm -rf`) ко всей папке на любую глубину.

## 3. Потоки, пайпы и обработка текста

### Стандартные потоки
- `0` (`stdin`) — ввод, `1` (`stdout`) — полезный вывод, `2` (`stderr`) — ошибки.

### Перенаправления
- `>` — stdout в файл с **перезаписью**.
- `>>` — stdout в файл с **дозаписью**.
- `2>` — только stderr в файл: `cat missing.txt 2> errors.log`.
- `2>&1` — склеить stderr со stdout: `ping -c 1 8.8.8.8 > /dev/null 2>&1` (весь вывод в «чёрную дыру»).
- `|` — stdout одной команды на stdin следующей.

### Инструменты
- `grep [опции] "шаблон" <файл>`: `-i` без учёта регистра, `-v` инверсия, `-n` номера строк, `-E` расширенные регулярки (`grep -E '404|500'`), `-L` имена файлов, где текста **нет**.
- `sort` — сортировка (`-n` числовая, `-r` обратная).
- `uniq` — убирает **подряд идущие** дубли, поэтому всегда после `sort`; `-c` считает повторы.
- `cut -d '%' -f 1` — вырезать колонку (`-d` разделитель, `-f` номер поля).
- `wc -l` — количество строк.
- `xargs` — превращает строки из пайпа в аргументы команды; `-r` не запускает команду при пустом вводе.
- `sed -i 's/old/new/g' file.txt` — замена в файле на месте.
- `awk '{print $1}'` — работа со столбцами (`$1`, `$2`, …).

### Готовые конвейеры
```bash
# Топ IP по статусу 200 (для 404 замени шаблон)
grep "200" access.log | awk '{print $1}' | sort | uniq -c | sort -nr | head -n 3

# Конфиг без комментариев и пустых строк
grep -Ev "^#|^$" /etc/nginx/nginx.conf
```

## 4. Переменные окружения и конфиги оболочки

- `env` — все переменные текущей сессии.
- `export VAR="value"` — сделать переменную глобальной. Вокруг `=` **нет пробелов**. `$` нужен только при чтении (`echo $VAR`). Имена чувствительны к регистру.
- `$PATH` — папки (через `:`), где ищутся исполняемые файлы.
  - Добавить путь, **сохранив старый**: `export PATH="$PATH:/home/user/my_folder"`.
  - Точка `.` в `$PATH` позволяет запускать скрипты из текущей папки по имени, но на реальных серверах это опасно: злоумышленник может подложить вредоносный файл в рабочую папку.
- `~/.bashrc` — выполняется при каждом открытии терминала (алиасы, постоянный `PATH`).
- `~/.bash_profile` / `~/.profile` — выполняются один раз при логине.

## 5. Bash-скрипты

Скрипт — текстовый файл `.sh`. Запуск: `bash script.sh` или `chmod +x script.sh && ./script.sh`.

### Коды возврата
- `$?` — код последней команды: `0` успех, `1–255` ошибка. CI/CD по ненулевому коду останавливает деплой.
- `exit 1` — прервать скрипт с ошибкой.

### Операторы в `[ ]` (пробелы внутри скобок обязательны)
- Числа: `-eq` равно, `-ne` не равно, `-gt` больше, `-lt` меньше, `-ge` больше или равно, `-le` меньше или равно.
- Строки и файлы: `-z "$VAR"` пустая строка, `-n "$VAR"` непустая, `-f файл` файл существует, `-d папка` папка существует.
- Переменные в `[ ]` лучше брать в кавычки.

### Шаблон скрипта
```bash
#!/bin/bash
# Шебанг указывает интерпретатор

# 1. Проверка обязательной переменной окружения
if [ -z "$DB_PASSWORD" ]; then
    echo "[ERROR] DB_PASSWORD не задан!" >&2
    exit 1
fi

# 2. Цикл по строкам файла servers.txt (while read надёжнее, чем for ... $(cat ...))
while read -r ip; do
    echo "--- Проверяю $ip ---"
    # if проверяет код возврата команды напрямую, без отдельного $?
    if ping -c 1 -W 1 "$ip" > /dev/null 2>&1; then
        echo "[OK] Сервер доступен, отправляю конфиг..."
        scp nginx.conf "wert@$ip:/tmp/"
    else
        echo "[WARNING] $ip недоступен или закрыт файрволом!"
    fi
done < servers.txt
# Если внутри такого цикла используется ssh, добавляй ssh -n,
# иначе он съест остаток servers.txt со stdin.
```

### Пример: мониторинг ресурсов (monitor.sh)
Нужны `bc`; для отправки алертов почтой ещё и `mail`.

```bash
#!/bin/bash
LOG_FILE="/var/log/monitor.log"    # запись в /var/log требует root
THRESHOLD_CPU=80
THRESHOLD_MEMORY=80
THRESHOLD_DISK=90

log_message() {
    echo "$(date '+%Y-%m-%d %H:%M:%S') - $1" >> "$LOG_FILE"
}

check_cpu() {
    local cpu
    cpu=$(top -bn1 | awk '/Cpu\(s\)/ {print $2 + $4}')    # user + system
    if (( $(echo "$cpu > $THRESHOLD_CPU" | bc -l) )); then
        log_message "WARNING: High CPU usage: ${cpu}%"
        # echo "High CPU: ${cpu}%" | mail -s "CPU Alert" admin@example.com
    fi
}

check_memory() {
    local mem
    mem=$(free | awk '/Mem/ {printf "%.1f", $3/$2*100}')
    if (( $(echo "$mem > $THRESHOLD_MEMORY" | bc -l) )); then
        log_message "WARNING: High memory usage: ${mem}%"
    fi
}

check_disk() {
    df -hP | grep -vE '^Filesystem|tmpfs|cdrom' | awk '{print $5, $1}' | while read -r usage partition; do
        usage=${usage%\%}
        if [ "$usage" -ge "$THRESHOLD_DISK" ]; then
            log_message "WARNING: High disk usage on $partition: ${usage}%"
        fi
    done
}

log_message "Starting system monitoring"
check_cpu
check_memory
check_disk
log_message "Monitoring completed"
```

Запуск по расписанию: см. cron и systemd timer в [разделе 8](#8-пакеты-службы-systemd-и-планировщик).

## 6. Права, пользователи и sudo

### Права доступа
- Три категории: **U**ser (владелец), **G**roup (группа), **O**thers (остальные).
- Права: `r` чтение, `w` запись, `x` запуск (для папки: вход в неё).
- Числовая запись: `r=4`, `w=2`, `x=1`. Примеры: `755` (rwxr-xr-x), `644` (rw-r--r--), `600` (rw-------). Права `777` опасны.
- `chmod +x script.sh` — сделать скрипт исполняемым.
- `chmod 600 ~/.ssh/id_ed25519` — приватный ключ должен быть доступен только владельцу.
- `chown user:group файл` — сменить владельца (`-R` для папки).

### Пользователи
- `sudo adduser devops` — интерактивное создание пользователя (удобно).
- `sudo useradd -m -s /bin/bash devops` — низкоуровневый вариант: `-m` создаёт домашнюю папку, `-s` задаёт оболочку.
- `sudo usermod -aG sudo devops` — добавить в группу sudo. Флаг `-a` критичен: без него пользователь пропадёт из остальных групп.
- Под `root` напрямую не работаем: повседневная работа идёт от обычного пользователя с `sudo`, действия логируются в `/var/log/auth.log`.

### Настройка sudo
- `sudo visudo` — безопасное редактирование `/etc/sudoers` (проверяет синтаксис).
- Sudo без пароля: `devops ALL=(ALL:ALL) NOPASSWD: ALL`. Допустимо в тестовой среде, на боевом сервере лучше ограничивать список команд.

## 7. Процессы и сигналы

### Состояния (колонка STAT в `ps aux`)
| Код | Состояние | Описание |
|-----|-----------|----------|
| `R` | Running | Выполняется или ждёт очереди к CPU |
| `S` | Interruptible Sleep | Ждёт событие (ввод, сеть, таймер); норма для большинства программ |
| `D` | Uninterruptible Sleep | Завис на I/O (диск, сетевая папка); не убивается даже `kill -9` |
| `T` | Stopped | Остановлен (например, `Ctrl+Z`) |
| `Z` | Zombie | Завершён, но родитель не прочитал код возврата; память освобождена, запись в таблице PID осталась |

Дополнительные символы: `<` высокий приоритет, `N` низкий приоритет, `s` лидер сессии, `l` многопоточный, `+` на переднем плане.

### Сигналы (`kill -<СИГНАЛ> <PID>`)
| Сигнал | Номер | Действие |
|--------|-------|----------|
| `SIGHUP` | 1 | Перечитать конфиг без остановки (Nginx и другие демоны) |
| `SIGINT` | 2 | Прерывание с клавиатуры (`Ctrl+C`) |
| `SIGKILL` | 9 | Мгновенное уничтожение ядром, процесс не успевает сохранить данные. Крайняя мера, опасно для БД |
| `SIGTERM` | 15 | Вежливое завершение; по умолчанию для `kill`. Стандарт в DevOps |
| `SIGSTOP` | 19 | Безусловная заморозка (перехватить нельзя). Продолжить: `SIGCONT` (18) |
| `SIGTSTP` | 20 | Пауза с клавиатуры (`Ctrl+Z`); процесс может её обработать |

Правило: сначала `kill <PID>` (15), и только если процесс завис, `kill -9 <PID>`.

### Инспекция
- `ps aux` — все процессы. Смотри колонку `RSS` (реальная RAM в КБ), а не `VSZ` (виртуальная).
- `ps aux | grep "[n]ginx"` — скобки вокруг первой буквы не дают `grep` найти самого себя.
- `pgrep -l nginx` — только PID и имя, без `grep`.
- `ps aux --sort=-%mem | head -n 6` — топ-5 по памяти (плюс строка заголовка).
- `ps axjf` / `ps auxf` — дерево процессов с PPID: видно, кто кого породил.
- `htop` (или `top`) — интерактивный монитор; в `htop` `F9` убивает процесс.
- `uptime` — аптайм и Load Average (1, 5, 15 минут). Если нагрузка заметно выше числа ядер, сервер перегружен.
- `strace -p <PID>` — системные вызовы процесса в реальном времени. Если приложение «зависло» и молчит в логах, видно, на каком файле или запросе оно застряло.
- `ulimit -n` — максимум открытых файлов для пользователя.

### Остановка
- `kill <PID>` — мягко (SIGTERM). `kill -9 <PID>` — жёстко.
- `pkill nginx` / `killall nginx` — отправить SIGTERM **всем** процессам с этим именем (с `-9` будет жёстко).

### Зомби
Зомби уже мёртв, убить его нельзя. Нужно разобраться с родителем.
```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'   # найти зомби и PPID
ps -o ppid= -p <ZOMBIE_PID>                  # PID родителя
```
Сначала перезапусти службу родителя (`sudo systemctl restart ...`) или отправь ему `kill <PPID>`. `kill -9 <PPID>` только в крайнем случае: ты убьёшь живой процесс.

## 8. Пакеты, службы (systemd) и планировщик

### Пакетный менеджер apt
- `sudo apt update` — обновить список пакетов (перед любой установкой).
- `sudo apt install -y <пакет>` — установить (`-y` автоматически соглашается).
  Пример: `sudo apt install -y openssh-server`.

### Управление службами
- `sudo systemctl start|stop|restart|status <служба>` — управление службой (старый вариант: `sudo service <служба> start`).
- `sudo systemctl enable <служба>` — автозапуск при старте сервера (`disable` — убрать).
- `sudo systemctl list-unit-files --type=service` — список служб.
- `journalctl -u <служба> -f` — живые логи службы (`-f` follow).

### Свой юнит (`/etc/systemd/system/my-app.service`)
```ini
[Unit]
Description=My DevOps App
After=network.target          # запуск после поднятия сети

[Service]
Type=simple
ExecStart=/home/wert/app.sh   # абсолютный путь
Restart=always                # перезапуск при падении
User=wert                     # запуск не от root

[Install]
WantedBy=multi-user.target    # автозапуск при старте ОС
```

После создания или правки файла:
```bash
sudo systemctl daemon-reload              # перечитать юниты
sudo systemctl start my-app.service       # запустить (внутри fork() и exec())
sudo systemctl enable my-app.service      # включить автозапуск
sudo systemctl status my-app.service      # статус, PID, ресурсы
```

### Лимиты ресурсов (cgroups v2 в секции `[Service]`)
- `MemoryMax=500M` — жёсткий лимит памяти; при превышении процесс убивает OOM Killer.
- `CPUAccounting=true` + `CPUQuota=50%` — максимум 50% одного ядра.

### Планировщик
**Cron:**
- `crontab -e` — редактировать расписание, `crontab -l` — показать.
- Формат: `минута час день_месяца месяц день_недели команда`.
  - `0 3 * * * /bin/bash /script.sh` — каждую ночь в 03:00.
  - `*/15 * * * * /bin/bash /script.sh` — каждые 15 минут.

**systemd timer** (современная замена; частоту ниже 1 минуты cron не умеет). Файл `my-monitor.timer` рядом с `my-monitor.service`:
```ini
[Unit]
Description=Run my-monitor.service every 30 seconds

[Timer]
OnBootSec=10sec               # первый запуск через 10 с после старта
OnUnitActiveSec=30sec         # дальше каждые 30 с после прошлого запуска
Unit=my-monitor.service

[Install]
WantedBy=timers.target
```
Включение: `sudo systemctl enable --now my-monitor.timer`.

## 9. Сеть

В современном Linux вместо устаревшего `net-tools` (`ifconfig`, `route`, `netstat`) используется **`iproute2`** (`ip`, `ss`).

### 9.1. Интерфейсы и адреса
- `ip a` — интерфейсы, статус (`UP`/`DOWN`), MAC и IP с масками. Быстрая проверка, получил ли интерфейс адрес по DHCP.
- `sudo ip address add 192.168.1.50/24 dev eth0` — добавить IP на интерфейс (миграции, плавающий VIP для отказоустойчивости).
- `sudo ip link set dev eth0 up|down` — включить/выключить интерфейс. Так имитируют аварию, проверяя High Availability.

### 9.2. Маршрутизация
Если адрес не из локальной сети, пакет уходит на **шлюз по умолчанию** (default gateway).
- `ip route show` (или `ip r`) — таблица маршрутов. Пример: `default via 192.168.1.1 dev eth0` значит «всё внешнее отправлять через 192.168.1.1 по eth0». Нет строки `default`, значит сервер изолирован, отсюда ошибка *Network is unreachable*.
- `sudo ip route add 10.10.0.0/16 via 192.168.1.254` — статический маршрут (например, к подсети БД через VPN-шлюз).

### 9.3. Виртуальные мосты (bridge)
Bridge — виртуальный коммутатор в памяти ядра, объединяющий интерфейсы в одну L2-сеть. Так работает Docker: создаёт мост `docker0` (например, `172.17.0.1/16`), подключает к нему каждый контейнер виртуальным «кабелем», а наружу трафик идёт через физическую карту с NAT.

```bash
sudo ip link add br0 type bridge        # создать мост
sudo ip link set dev br0 up             # включить
sudo ip link set eth1 master br0        # «воткнуть» eth1 в мост
ip link show master br0                 # что подключено (или: bridge link)
```

### 9.4. Диагностика
**Доступность и маршрут**
- `ping -c 4 8.8.8.8` — 4 ICMP-пакета. Если IP пингуется, а `ping google.com` нет, сеть работает, а сломан DNS (смотри `/etc/resolv.conf`).
- `traceroute -n google.com` / `mtr google.com` — цепочка роутеров до цели, видно, где обрыв (`-n` без поиска имён).

**DNS**
- `dig google.com` — подробно, `nslookup google.com` / `host google.com` — коротко.

**Порты и соединения**
- `ss -tlnp` — кто слушает порты. Слушает `127.0.0.1:8080`, значит снаружи недоступно; `0.0.0.0:8080` — открыто всем; порта нет в списке — приложение не стартовало.
- `ss -tulpn` — то же, включая UDP (замена `netstat -tulpn`).
- `nc -zv <хост> 22` — проверить порт на удалённом хосте (или `telnet <хост> 22`).
- Проверка порта без дополнительных утилит, только Bash:
  `timeout 3 bash -c 'cat < /dev/null > /dev/tcp/google.com/80' && echo Open || echo Closed`

**HTTP**
- `curl -I https://google.com` — только заголовки ответа (`200`, `301`, `502`).
- `curl -s <url>` — запрос к API, `curl -O <url>` / `wget <url>` — скачать файл.

### 9.5. tcpdump — сниффер
Убирает гадание: показывает, дошёл ли пакет до сервера и что сервер ответил.

Пример: приложение не достучалось до БД (`Connection timeout`), хотя файрвол в порядке. Запускаем `tcpdump` на сервере БД:
- **Пакеты не приходят**, значит проблема в сети или на маршруте до сервера.
- **Приходят, но ответы не доходят обратно**, значит сломан обратный маршрут.

```bash
sudo tcpdump -i eth0 -n -c 10 ip               # 10 пакетов, только IP-адреса, без имён
sudo tcpdump -A -i eth0 port 80                # содержимое HTTP как текст (HTTPS зашифрован)
sudo tcpdump -i any port 53                    # работает ли DNS
sudo tcpdump -i eth0 src 192.168.1.100         # только трафик от конкретного хоста
sudo tcpdump -i eth0 -w dump.pcap              # записать в файл для Wireshark
```

## 10. Безопасность сервера (hardening)

Чек-лист для нового сервера.

**1. Обычный пользователь вместо root**
```bash
sudo adduser devops_jun
sudo usermod -aG sudo devops_jun
```

**2. Вход по SSH-ключам**
```bash
ssh-keygen -t ed25519 -C "key_label"                      # на своём ПК
ssh-copy-id -i ~/.ssh/id_ed25519.pub devops_jun@<IP>      # положить публичный ключ на сервер
```
Ключ попадает в `~/.ssh/authorized_keys` пользователя на сервере.

**3. Закрыть SSH-демон** (`sudo vim /etc/ssh/sshd_config`)
- `PasswordAuthentication no` — вход только по ключам (защита от брутфорса).
- `PermitRootLogin no` — запрет прямого входа под root.

Применить: `sudo systemctl restart ssh` (на Ubuntu/Debian служба называется `ssh`, на RHEL-семействе `sshd`).

> **Перед перезапуском и закрытием сессии** открой вторую сессию и убедись, что вход по ключу работает. Иначе можно запереть себя на сервере.

**4. Файрвол UFW**
```bash
sudo apt update && sudo apt install -y ufw
sudo ufw allow 22/tcp          # ОБЯЗАТЕЛЬНО до включения, иначе потеряешь доступ
sudo ufw enable                # остальные входящие порты закрыты
sudo ufw status verbose        # аудит правил
```

> **Docker обходит UFW:** порты, опубликованные через `-p` / `ports:`, Docker открывает правилами iptables напрямую. На сервере публикуй порты на loopback (`"127.0.0.1:8081:8080"`) и выставляй наружу через reverse proxy.

**5. Дополнительно:** обновления безопасности (`unattended-upgrades`), `fail2ban`, логи в `/var/log/auth.log`, отсутствие `.` в `$PATH`, аудит прав (`find ... -perm 777`).

## 11. Docker

### 11.1. Контейнер и виртуальная машина
- **ВМ** эмулирует железо и запускает **своё ядро ОС**: тяжело, долгий старт.
- **Контейнер** использует **ядро хоста** и запускает изолированный процесс (namespaces + cgroups). Весит мегабайты, стартует за доли секунды.

### 11.2. Архитектура
- **Docker Daemon** (`dockerd`) — служба от root: скачивает образы, создаёт сети, запускает контейнеры.
- **Docker Client** (`docker`) — CLI, отправляет REST-запросы демону через Unix-сокет.
- **Образ (image)** — неизменяемый шаблон (как класс в ООП). **Контейнер** — запущенный экземпляр образа (как объект). Из одного образа можно запустить сколько угодно контейнеров.
- Доступ к Docker-сокету равен root-доступу на хосте, поэтому в группу `docker` добавляем осознанно.

### 11.3. Команды

**Образы**
- `docker images` — локальные образы.
- `docker pull <образ>` — скачать, не запуская.
- `docker rmi <ID>` — удалить (нельзя, если есть контейнер на его основе, даже остановленный).
- `docker tag <старый> <новый>:<версия>` — задать имя/версию. Без версии ставится `latest`; в проде версии фиксируем.
- `docker history <ID>` — слои и команды сборки (почему образ тяжёлый).
- `docker push <образ>` — отправить в Docker Hub или приватный registry.

**Контейнеры**
- `docker run -d -p 8080:80 --name my-web nginx` — создать и запустить: `-d` в фоне, `-p хост:контейнер`, `--name` имя.
- `docker ps` — запущенные; `docker ps -a` — все, включая остановленные.
- `docker stop <имя>` — SIGTERM, а если процесс не завершился за 10 секунд, SIGKILL. Статус `Exited`.
- `docker rm <имя>` — удалить контейнер. Данные внутри, не вынесенные в volume, исчезнут.
- `docker logs -f <имя>` — живые логи.
- `docker exec -it <имя> bash` — терминал внутри контейнера (в alpine-образах `sh`).
- `docker system prune` — удалить неиспользуемое (контейнеры, сети, образы); внимательно.

**Сети**
- `docker network ls` — сети (по умолчанию `bridge`, `host`, `none`).
- `docker network create <имя>` — своя изолированная сеть. Контейнеры в ней видят друг друга **по имени** через встроенный DNS, а снаружи до них не добраться, пока порты не опубликованы. Это базовая практика безопасности.

### 11.4. Типы сетей (`--network <тип>`)
| Тип | Как работает | Когда использовать |
|-----|--------------|--------------------|
| **bridge** (по умолчанию) | Виртуальный свитч на хосте, у контейнера свой внутренний IP (например, `172.17.0.2`). Наружу только через `-p`, трафик идёт через NAT | Основной режим изоляции приложений |
| **host** | Нет сетевой изоляции: контейнер использует сетевой стек хоста, `-p` не нужен | Максимальная скорость без накладных расходов NAT (тяжёлые БД, сбор логов) |
| **none** | Только `lo`, ни сети, ни интернета | Обработка секретов: код не сможет ничего отправить наружу |
| **overlay** | Туннель между контейнерами на разных машинах (Swarm/Kubernetes) | Кластеры |
| **macvlan** | Контейнер получает собственный MAC и IP от роутера, выглядит как отдельный компьютер | Интеграция с физической сетью |

### 11.5. Dockerfile
Файл называется строго `Dockerfile` (без расширения). Каждая инструкция `FROM`/`RUN`/`COPY` создаёт неизменяемый **слой**; неизменяемые слои кэшируются, поэтому порядок инструкций влияет на скорость сборки.

**Инструкции сборки**
- `FROM python:3.10-slim` — базовый образ (первая строка; фиксируй версию).
- `RUN apt-get update && apt-get install -y htop` — команда **при сборке**.
- `COPY ./app.py /app/` — копировать файлы с хоста в образ. `ADD` умеет ещё скачивать по URL и распаковывать архивы, но для обычного копирования используй `COPY`.
- `WORKDIR /app` — аналог `cd` для следующих инструкций.
- `ENV APP_ENV=production` — переменная, доступная и в запущенном контейнере.
- `ARG VERSION=1.0` — переменная **только на время сборки**.
- `EXPOSE 8080` — документация порта; сама порт **не** открывает, нужен `-p`.
- `USER devops` — запуск не от root: при взломе приложения злоумышленник не получит root.

**Инструкции запуска** (выполняются при старте контейнера)
- `CMD ["python", "main.py"]` — команда по умолчанию, **легко переопределяется** в `docker run`.
- `ENTRYPOINT ["nginx", "-g", "daemon off;"]` — фиксированная точка входа (переопределить можно только через `--entrypoint`).
- Используй **exec-форму** (`["…", "…"]`, а не строку): тогда процесс становится PID 1 и получает сигналы (`SIGTERM`) напрямую. Если процесс не обрабатывает сигналы, добавляй `init: true` / `--init`.

**Практики**
- Порядок слоёв: сначала зависимости (`COPY package*.json` + `npm ci`), потом исходники. Тогда кэш переиспользуется.
- **Multi-stage build**: тяжёлый этап сборки (Node, компилятор) отдельно, в финальный образ копируются только артефакты (`COPY --from=build /app/dist ...`).
- `.dockerignore`: исключить `node_modules`, `.env`, `.git`, артефакты сборки.
- Не клади секреты в образ (`ENV`, `COPY .env`): передавай их при запуске.

### 11.6. Docker Compose (v2: `docker compose`)
Описывает многоконтейнерное приложение в `docker-compose.yml`: сервисы, сети, тома, переменные.

- `docker compose up -d --build` — собрать и запустить в фоне.
- `docker compose ps` — состояние (смотри `healthy` у сервисов с healthcheck).
- `docker compose logs -f <сервис>` — живые логи.
- `docker compose exec <сервис> sh` — зайти внутрь.
- `docker compose config` — итоговый файл после подстановки переменных (удобно для отладки).
- `docker compose down` — остановить и удалить контейнеры, данные в именованных томах сохраняются.
- `docker compose down -v` — то же **и удалить тома** (данные пропадут).

Что важно в `docker-compose.yml`:
- `depends_on` с `condition: service_healthy` — порядок старта по готовности, а не просто по запуску.
- `healthcheck` — проверка здоровья сервиса. В `test` знак `$` экранируется как `$$`, чтобы переменную подставил shell контейнера, а не Compose.
- `volumes` (именованные тома) — данные переживают пересоздание контейнеров.
- `restart: unless-stopped` — автоперезапуск.
- Секреты через `.env` (в `.gitignore`) плюс `.env.example` как шаблон в репозитории.
- Наружу публикуй только то, что нужно (обычно один входной сервис).
