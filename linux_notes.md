## 1. Git

Путь изменений: **рабочая директория** → **индекс (staging)** → **локальный коммит** → **удалённый репозиторий** (GitHub/GitLab).

- `git clone <url>` — скопировать репозиторий.
- `git status` — главная команда контроля.
  - Красные файлы (untracked / modified): изменения только на твоём ПК.
  - Зелёные файлы (staged): добавлены в индекс, готовы к коммиту.
- `git add .` — добавить в индекс все изменения в текущей папке.
- `git add <файл>` — добавить один файл.
- `git reset` — убрать всё из индекса. Файлы на диске не меняются.
- `git commit -m "тип: описание"` — зафиксировать индекс в коммит.
- `git push` / `git pull` — отправить / забрать коммиты.
- `git log --oneline` — краткая история, `git diff` — что изменилось.
- `git switch -c <ветка>` — создать ветку и перейти в неё.

**Conventional Commits:** `feat:` новая функциональность, `fix:` исправление, `docs:` документация, `chore:` наведение порядка.

**Важно:** секреты (`.env`, ключи, пароли) в репозиторий не коммитим, а добавляем в `.gitignore`. Если секрет попал в историю, удаления файла недостаточно: ключ нужно перевыпустить.

## 2. Файлы и навигация

### Просмотр и аудит
- `pwd` — текущий абсолютный путь.
- `ls -la` — список файлов, включая скрытые, с правами.
- `tree` — структура папки деревом.
- `file <имя>` — реальный тип файла по сигнатуре, а не по расширению.
- `stat <имя>` — размер, владелец, права, три даты.
- `du -sh /var/log/*` — вес папок и файлов (`-s` сумма, `-h` человекочитаемо). Помогает найти, что «съело» диск.
- `df -h` — свободное место по разделам.

### Поиск: `find` и `locate`
- `find <где> -name "<маска>"` — флаг `-name` обязателен: в `find . "*.sh"` маска будет принята за путь и вернётся ошибка.
- `locate <имя>` — мгновенный поиск по готовой базе. После создания новых файлов нужен `sudo updatedb`.

```bash
find . -name "*.md"                                           # по имени
sudo find /var/ -type f -size +1G                             # по размеру (M, k — мега/килобайты)
sudo find /etc/ -type f -mtime -3                             # изменены за 3 дня (следы взлома)
sudo find /var/www/ -type f -perm 777                         # опасные права (аудит)
sudo find /etc/ -type f \( -name "*.key" -o -name "*.txt" \) -mtime -2   # .key ИЛИ .txt
sudo find /tmp/ -type f -name "*.tmp" -mtime +7 -delete       # удалить старые временные
find . -name "*.log" | xargs -r rm                            # удалить найденное через xargs
```

### Ссылки
- `ln <файл> <ссылка>` — **жёсткая** ссылка: те же данные на диске. Оригинал удалён, ссылка работает. Не работает между разделами и для папок.
- `ln -s <файл> <ссылка>` — **символическая** (как ярлык в Windows). Оригинал удалён, ссылка «битая».

### Архивы, диски, очистка
- `sudo tar -czvf ~/backup.tar.gz /etc/nginx/` — создать (`c`) сжатый gzip (`z`) архив с выводом процесса (`v`) в файл (`f`). Распаковать: `tar -xzvf backup.tar.gz`.
- `sudo mount /dev/loop0 /mnt/backup` — примонтировать диск в папку.
- `sudo truncate -s 0 /var/log/app.log` — обнулить файл, не удаляя его и не ломая запущенную программу.
- `echo -n "" | sudo tee /var/log/app.log` — альтернатива, когда обычное перенаправление даёт `Permission denied`.
- `lsof /var/log/app.log` — какой процесс держит файл.
- `lsof | grep deleted` — файлы, удалённые через `rm`, но всё ещё занимающие место, потому что процесс их не закрыл. Лечится перезапуском процесса.
- `sudo cp /proc/<PID>/exe ~/recovered_file` — восстановить удалённый бинарник работающего процесса.
- Рекурсия: флаг `-r` / `-R` применяет команду (`chmod -R`, `chown -R`, `rm -rf`) ко всей папке на любую глубину.

## 3. Потоки, пайпы и обработка текста

### Стандартные потоки
- `0` (`stdin`) — ввод, `1` (`stdout`) — полезный вывод, `2` (`stderr`) — ошибки.

### Перенаправления
- `>` — stdout в файл с **перезаписью**.
- `>>` — stdout в файл с **дозаписью**.
- `2>` — только stderr в файл: `cat missing.txt 2> errors.log`.
- `2>&1` — склеить stderr со stdout: `ping -c 1 8.8.8.8 > /dev/null 2>&1` (весь вывод в «чёрную дыру»).
- `|` — stdout одной команды на stdin следующей.

### Инструменты
- `grep [опции] "шаблон" <файл>`: `-i` без учёта регистра, `-v` инверсия, `-n` номера строк, `-E` расширенные регулярки (`grep -E '404|500'`), `-L` имена файлов, где текста **нет**.
- `sort` — сортировка (`-n` числовая, `-r` обратная).
- `uniq` — убирает **подряд идущие** дубли, поэтому всегда после `sort`; `-c` считает повторы.
- `cut -d '%' -f 1` — вырезать колонку (`-d` разделитель, `-f` номер поля).
- `wc -l` — количество строк.
- `xargs` — превращает строки из пайпа в аргументы команды; `-r` не запускает команду при пустом вводе.
- `sed -i 's/old/new/g' file.txt` — замена в файле на месте.
- `awk '{print $1}'` — работа со столбцами (`$1`, `$2`, …).

### Готовые конвейеры
```bash
# Топ IP по статусу 200 (для 404 замени шаблон)
grep "200" access.log | awk '{print $1}' | sort | uniq -c | sort -nr | head -n 3

# Конфиг без комментариев и пустых строк
grep -Ev "^#|^$" /etc/nginx/nginx.conf
```

## 4. Переменные окружения и конфиги оболочки

- `env` — все переменные текущей сессии.
- `export VAR="value"` — сделать переменную глобальной. Вокруг `=` **нет пробелов**. `$` нужен только при чтении (`echo $VAR`). Имена чувствительны к регистру.
- `$PATH` — папки (через `:`), где ищутся исполняемые файлы.
  - Добавить путь, **сохранив старый**: `export PATH="$PATH:/home/user/my_folder"`.
  - Точка `.` в `$PATH` позволяет запускать скрипты из текущей папки по имени, но на реальных серверах это опасно: злоумышленник может подложить вредоносный файл в рабочую папку.
- `~/.bashrc` — выполняется при каждом открытии терминала (алиасы, постоянный `PATH`).
- `~/.bash_profile` / `~/.profile` — выполняются один раз при логине.

## 5. Bash-скрипты

Скрипт — текстовый файл `.sh`. Запуск: `bash script.sh` или `chmod +x script.sh && ./script.sh`.

### Коды возврата
- `$?` — код последней команды: `0` успех, `1–255` ошибка. CI/CD по ненулевому коду останавливает деплой.
- `exit 1` — прервать скрипт с ошибкой.

### Операторы в `[ ]` (пробелы внутри скобок обязательны)
- Числа: `-eq` равно, `-ne` не равно, `-gt` больше, `-lt` меньше, `-ge` больше или равно, `-le` меньше или равно.
- Строки и файлы: `-z "$VAR"` пустая строка, `-n "$VAR"` непустая, `-f файл` файл существует, `-d папка` папка существует.
- Переменные в `[ ]` лучше брать в кавычки.

### Шаблон скрипта
```bash
#!/bin/bash
# Шебанг указывает интерпретатор

# 1. Проверка обязательной переменной окружения
if [ -z "$DB_PASSWORD" ]; then
    echo "[ERROR] DB_PASSWORD не задан!" >&2
    exit 1
fi

# 2. Цикл по строкам файла servers.txt (while read надёжнее, чем for ... $(cat ...))
while read -r ip; do
    echo "--- Проверяю $ip ---"
    # if проверяет код возврата команды напрямую, без отдельного $?
    if ping -c 1 -W 1 "$ip" > /dev/null 2>&1; then
        echo "[OK] Сервер доступен, отправляю конфиг..."
        scp nginx.conf "wert@$ip:/tmp/"
    else
        echo "[WARNING] $ip недоступен или закрыт файрволом!"
    fi
done < servers.txt
# Если внутри такого цикла используется ssh, добавляй ssh -n,
# иначе он съест остаток servers.txt со stdin.
```

### Пример: мониторинг ресурсов (monitor.sh)
Нужны `bc`; для отправки алертов почтой ещё и `mail`.

```bash
#!/bin/bash
LOG_FILE="/var/log/monitor.log"    # запись в /var/log требует root
THRESHOLD_CPU=80
THRESHOLD_MEMORY=80
THRESHOLD_DISK=90

log_message() {
    echo "$(date '+%Y-%m-%d %H:%M:%S') - $1" >> "$LOG_FILE"
}

check_cpu() {
    local cpu
    cpu=$(top -bn1 | awk '/Cpu\(s\)/ {print $2 + $4}')    # user + system
    if (( $(echo "$cpu > $THRESHOLD_CPU" | bc -l) )); then
        log_message "WARNING: High CPU usage: ${cpu}%"
        # echo "High CPU: ${cpu}%" | mail -s "CPU Alert" admin@example.com
    fi
}

check_memory() {
    local mem
    mem=$(free | awk '/Mem/ {printf "%.1f", $3/$2*100}')
    if (( $(echo "$mem > $THRESHOLD_MEMORY" | bc -l) )); then
        log_message "WARNING: High memory usage: ${mem}%"
    fi
}

check_disk() {
    df -hP | grep -vE '^Filesystem|tmpfs|cdrom' | awk '{print $5, $1}' | while read -r usage partition; do
        usage=${usage%\%}
        if [ "$usage" -ge "$THRESHOLD_DISK" ]; then
            log_message "WARNING: High disk usage on $partition: ${usage}%"
        fi
    done
}

log_message "Starting system monitoring"
check_cpu
check_memory
check_disk
log_message "Monitoring completed"
```

Запуск по расписанию: см. cron и systemd timer в [разделе 8](#8-пакеты-службы-systemd-и-планировщик).

## 6. Права, пользователи и sudo

### Права доступа
- Три категории: **U**ser (владелец), **G**roup (группа), **O**thers (остальные).
- Права: `r` чтение, `w` запись, `x` запуск (для папки: вход в неё).
- Числовая запись: `r=4`, `w=2`, `x=1`. Примеры: `755` (rwxr-xr-x), `644` (rw-r--r--), `600` (rw-------). Права `777` опасны.
- `chmod +x script.sh` — сделать скрипт исполняемым.
- `chmod 600 ~/.ssh/id_ed25519` — приватный ключ должен быть доступен только владельцу.
- `chown user:group файл` — сменить владельца (`-R` для папки).

### Пользователи
- `sudo adduser devops` — интерактивное создание пользователя (удобно).
- `sudo useradd -m -s /bin/bash devops` — низкоуровневый вариант: `-m` создаёт домашнюю папку, `-s` задаёт оболочку.
- `sudo usermod -aG sudo devops` — добавить в группу sudo. Флаг `-a` критичен: без него пользователь пропадёт из остальных групп.
- Под `root` напрямую не работаем: повседневная работа идёт от обычного пользователя с `sudo`, действия логируются в `/var/log/auth.log`.

### Настройка sudo
- `sudo visudo` — безопасное редактирование `/etc/sudoers` (проверяет синтаксис).
- Sudo без пароля: `devops ALL=(ALL:ALL) NOPASSWD: ALL`. Допустимо в тестовой среде, на боевом сервере лучше ограничивать список команд.

## 7. Процессы и сигналы

### Состояния (колонка STAT в `ps aux`)
| Код | Состояние | Описание |
|-----|-----------|----------|
| `R` | Running | Выполняется или ждёт очереди к CPU |
| `S` | Interruptible Sleep | Ждёт событие (ввод, сеть, таймер); норма для большинства программ |
| `D` | Uninterruptible Sleep | Завис на I/O (диск, сетевая папка); не убивается даже `kill -9` |
| `T` | Stopped | Остановлен (например, `Ctrl+Z`) |
| `Z` | Zombie | Завершён, но родитель не прочитал код возврата; память освобождена, запись в таблице PID осталась |

Дополнительные символы: `<` высокий приоритет, `N` низкий приоритет, `s` лидер сессии, `l` многопоточный, `+` на переднем плане.

### Сигналы (`kill -<СИГНАЛ> <PID>`)
| Сигнал | Номер | Действие |
|--------|-------|----------|
| `SIGHUP` | 1 | Перечитать конфиг без остановки (Nginx и другие демоны) |
| `SIGINT` | 2 | Прерывание с клавиатуры (`Ctrl+C`) |
| `SIGKILL` | 9 | Мгновенное уничтожение ядром, процесс не успевает сохранить данные. Крайняя мера, опасно для БД |
| `SIGTERM` | 15 | Вежливое завершение; по умолчанию для `kill`. Стандарт в DevOps |
| `SIGSTOP` | 19 | Безусловная заморозка (перехватить нельзя). Продолжить: `SIGCONT` (18) |
| `SIGTSTP` | 20 | Пауза с клавиатуры (`Ctrl+Z`); процесс может её обработать |

Правило: сначала `kill <PID>` (15), и только если процесс завис, `kill -9 <PID>`.

### Инспекция
- `ps aux` — все процессы. Смотри колонку `RSS` (реальная RAM в КБ), а не `VSZ` (виртуальная).
- `ps aux | grep "[n]ginx"` — скобки вокруг первой буквы не дают `grep` найти самого себя.
- `pgrep -l nginx` — только PID и имя, без `grep`.
- `ps aux --sort=-%mem | head -n 6` — топ-5 по памяти (плюс строка заголовка).
- `ps axjf` / `ps auxf` — дерево процессов с PPID: видно, кто кого породил.
- `htop` (или `top`) — интерактивный монитор; в `htop` `F9` убивает процесс.
- `uptime` — аптайм и Load Average (1, 5, 15 минут). Если нагрузка заметно выше числа ядер, сервер перегружен.
- `strace -p <PID>` — системные вызовы процесса в реальном времени. Если приложение «зависло» и молчит в логах, видно, на каком файле или запросе оно застряло.
- `ulimit -n` — максимум открытых файлов для пользователя.

### Остановка
- `kill <PID>` — мягко (SIGTERM). `kill -9 <PID>` — жёстко.
- `pkill nginx` / `killall nginx` — отправить SIGTERM **всем** процессам с этим именем (с `-9` будет жёстко).

### Зомби
Зомби уже мёртв, убить его нельзя. Нужно разобраться с родителем.
```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'   # найти зомби и PPID
ps -o ppid= -p <ZOMBIE_PID>                  # PID родителя
```
Сначала перезапусти службу родителя (`sudo systemctl restart ...`) или отправь ему `kill <PPID>`. `kill -9 <PPID>` только в крайнем случае: ты убьёшь живой процесс.

## 8. Пакеты, службы (systemd) и планировщик

### Пакетный менеджер apt
- `sudo apt update` — обновить список пакетов (перед любой установкой).
- `sudo apt install -y <пакет>` — установить (`-y` автоматически соглашается).
  Пример: `sudo apt install -y openssh-server`.

### Управление службами
- `sudo systemctl start|stop|restart|status <служба>` — управление службой (старый вариант: `sudo service <служба> start`).
- `sudo systemctl enable <служба>` — автозапуск при старте сервера (`disable` — убрать).
- `sudo systemctl list-unit-files --type=service` — список служб.
- `journalctl -u <служба> -f` — живые логи службы (`-f` follow).

### Свой юнит (`/etc/systemd/system/my-app.service`)
```ini
[Unit]
Description=My DevOps App
After=network.target          # запуск после поднятия сети

[Service]
Type=simple
ExecStart=/home/wert/app.sh   # абсолютный путь
Restart=always                # перезапуск при падении
User=wert                     # запуск не от root

[Install]
WantedBy=multi-user.target    # автозапуск при старте ОС
```

После создания или правки файла:
```bash
sudo systemctl daemon-reload              # перечитать юниты
sudo systemctl start my-app.service       # запустить (внутри fork() и exec())
sudo systemctl enable my-app.service      # включить автозапуск
sudo systemctl status my-app.service      # статус, PID, ресурсы
```

### Лимиты ресурсов (cgroups v2 в секции `[Service]`)
- `MemoryMax=500M` — жёсткий лимит памяти; при превышении процесс убивает OOM Killer.
- `CPUAccounting=true` + `CPUQuota=50%` — максимум 50% одного ядра.

### Планировщик
**Cron:**
- `crontab -e` — редактировать расписание, `crontab -l` — показать.
- Формат: `минута час день_месяца месяц день_недели команда`.
  - `0 3 * * * /bin/bash /script.sh` — каждую ночь в 03:00.
  - `*/15 * * * * /bin/bash /script.sh` — каждые 15 минут.

**systemd timer** (современная замена; частоту ниже 1 минуты cron не умеет). Файл `my-monitor.timer` рядом с `my-monitor.service`:
```ini
[Unit]
Description=Run my-monitor.service every 30 seconds

[Timer]
OnBootSec=10sec               # первый запуск через 10 с после старта
OnUnitActiveSec=30sec         # дальше каждые 30 с после прошлого запуска
Unit=my-monitor.service

[Install]
WantedBy=timers.target
```
Включение: `sudo systemctl enable --now my-monitor.timer`.

## 9. Сеть

В современном Linux вместо устаревшего `net-tools` (`ifconfig`, `route`, `netstat`) используется **`iproute2`** (`ip`, `ss`).

### 9.1. Интерфейсы и адреса
- `ip a` — интерфейсы, статус (`UP`/`DOWN`), MAC и IP с масками. Быстрая проверка, получил ли интерфейс адрес по DHCP.
- `sudo ip address add 192.168.1.50/24 dev eth0` — добавить IP на интерфейс (миграции, плавающий VIP для отказоустойчивости).
- `sudo ip link set dev eth0 up|down` — включить/выключить интерфейс. Так имитируют аварию, проверяя High Availability.

### 9.2. Маршрутизация
Если адрес не из локальной сети, пакет уходит на **шлюз по умолчанию** (default gateway).
- `ip route show` (или `ip r`) — таблица маршрутов. Пример: `default via 192.168.1.1 dev eth0` значит «всё внешнее отправлять через 192.168.1.1 по eth0». Нет строки `default`, значит сервер изолирован, отсюда ошибка *Network is unreachable*.
- `sudo ip route add 10.10.0.0/16 via 192.168.1.254` — статический маршрут (например, к подсети БД через VPN-шлюз).

### 9.3. Виртуальные мосты (bridge)
Bridge — виртуальный коммутатор в памяти ядра, объединяющий интерфейсы в одну L2-сеть. Так работает Docker: создаёт мост `docker0` (например, `172.17.0.1/16`), подключает к нему каждый контейнер виртуальным «кабелем», а наружу трафик идёт через физическую карту с NAT.

```bash
sudo ip link add br0 type bridge        # создать мост
sudo ip link set dev br0 up             # включить
sudo ip link set eth1 master br0        # «воткнуть» eth1 в мост
ip link show master br0                 # что подключено (или: bridge link)
```

### 9.4. Диагностика
**Доступность и маршрут**
- `ping -c 4 8.8.8.8` — 4 ICMP-пакета. Если IP пингуется, а `ping google.com` нет, сеть работает, а сломан DNS (смотри `/etc/resolv.conf`).
- `traceroute -n google.com` / `mtr google.com` — цепочка роутеров до цели, видно, где обрыв (`-n` без поиска имён).

**DNS**
- `dig google.com` — подробно, `nslookup google.com` / `host google.com` — коротко.

**Порты и соединения**
- `ss -tlnp` — кто слушает порты. Слушает `127.0.0.1:8080`, значит снаружи недоступно; `0.0.0.0:8080` — открыто всем; порта нет в списке — приложение не стартовало.
- `ss -tulpn` — то же, включая UDP (замена `netstat -tulpn`).
- `nc -zv <хост> 22` — проверить порт на удалённом хосте (или `telnet <хост> 22`).
- Проверка порта без дополнительных утилит, только Bash:
  `timeout 3 bash -c 'cat < /dev/null > /dev/tcp/google.com/80' && echo Open || echo Closed`

**HTTP**
- `curl -I https://google.com` — только заголовки ответа (`200`, `301`, `502`).
- `curl -s <url>` — запрос к API, `curl -O <url>` / `wget <url>` — скачать файл.

### 9.5. tcpdump — сниффер
Убирает гадание: показывает, дошёл ли пакет до сервера и что сервер ответил.

Пример: приложение не достучалось до БД (`Connection timeout`), хотя файрвол в порядке. Запускаем `tcpdump` на сервере БД:
- **Пакеты не приходят**, значит проблема в сети или на маршруте до сервера.
- **Приходят, но ответы не доходят обратно**, значит сломан обратный маршрут.

```bash
sudo tcpdump -i eth0 -n -c 10 ip               # 10 пакетов, только IP-адреса, без имён
sudo tcpdump -A -i eth0 port 80                # содержимое HTTP как текст (HTTPS зашифрован)
sudo tcpdump -i any port 53                    # работает ли DNS
sudo tcpdump -i eth0 src 192.168.1.100         # только трафик от конкретного хоста
sudo tcpdump -i eth0 -w dump.pcap              # записать в файл для Wireshark
```

## 10. Безопасность сервера (hardening)

Чек-лист для нового сервера.

**1. Обычный пользователь вместо root**
```bash
sudo adduser devops_jun
sudo usermod -aG sudo devops_jun
```

**2. Вход по SSH-ключам**
```bash
ssh-keygen -t ed25519 -C "key_label"                      # на своём ПК
ssh-copy-id -i ~/.ssh/id_ed25519.pub devops_jun@<IP>      # положить публичный ключ на сервер
```
Ключ попадает в `~/.ssh/authorized_keys` пользователя на сервере.

**3. Закрыть SSH-демон** (`sudo vim /etc/ssh/sshd_config`)
- `PasswordAuthentication no` — вход только по ключам (защита от брутфорса).
- `PermitRootLogin no` — запрет прямого входа под root.

Применить: `sudo systemctl restart ssh` (на Ubuntu/Debian служба называется `ssh`, на RHEL-семействе `sshd`).

> **Перед перезапуском и закрытием сессии** открой вторую сессию и убедись, что вход по ключу работает. Иначе можно запереть себя на сервере.

**4. Файрвол UFW**
```bash
sudo apt update && sudo apt install -y ufw
sudo ufw allow 22/tcp          # ОБЯЗАТЕЛЬНО до включения, иначе потеряешь доступ
sudo ufw enable                # остальные входящие порты закрыты
sudo ufw status verbose        # аудит правил
```

> **Docker обходит UFW:** порты, опубликованные через `-p` / `ports:`, Docker открывает правилами iptables напрямую. На сервере публикуй порты на loopback (`"127.0.0.1:8081:8080"`) и выставляй наружу через reverse proxy.

**5. Дополнительно:** обновления безопасности (`unattended-upgrades`), `fail2ban`, логи в `/var/log/auth.log`, отсутствие `.` в `$PATH`, аудит прав (`find ... -perm 777`).

## 11. Docker

### 11.1. Контейнер и виртуальная машина
- **ВМ** эмулирует железо и запускает **своё ядро ОС**: тяжело, долгий старт.
- **Контейнер** использует **ядро хоста** и запускает изолированный процесс (namespaces + cgroups). Весит мегабайты, стартует за доли секунды.

### 11.2. Архитектура
- **Docker Daemon** (`dockerd`) — служба от root: скачивает образы, создаёт сети, запускает контейнеры.
- **Docker Client** (`docker`) — CLI, отправляет REST-запросы демону через Unix-сокет.
- **Образ (image)** — неизменяемый шаблон (как класс в ООП). **Контейнер** — запущенный экземпляр образа (как объект). Из одного образа можно запустить сколько угодно контейнеров.
- Доступ к Docker-сокету равен root-доступу на хосте, поэтому в группу `docker` добавляем осознанно.

### 11.3. Команды

**Образы**
- `docker images` — локальные образы.
- `docker pull <образ>` — скачать, не запуская.
- `docker rmi <ID>` — удалить (нельзя, если есть контейнер на его основе, даже остановленный).
- `docker tag <старый> <новый>:<версия>` — задать имя/версию. Без версии ставится `latest`; в проде версии фиксируем.
- `docker history <ID>` — слои и команды сборки (почему образ тяжёлый).
- `docker push <образ>` — отправить в Docker Hub или приватный registry.

**Контейнеры**
- `docker run -d -p 8080:80 --name my-web nginx` — создать и запустить: `-d` в фоне, `-p хост:контейнер`, `--name` имя.
- `docker ps` — запущенные; `docker ps -a` — все, включая остановленные.
- `docker stop <имя>` — SIGTERM, а если процесс не завершился за 10 секунд, SIGKILL. Статус `Exited`.
- `docker rm <имя>` — удалить контейнер. Данные внутри, не вынесенные в volume, исчезнут.
- `docker logs -f <имя>` — живые логи.
- `docker exec -it <имя> bash` — терминал внутри контейнера (в alpine-образах `sh`).
- `docker system prune` — удалить неиспользуемое (контейнеры, сети, образы); внимательно.

**Сети**
- `docker network ls` — сети (по умолчанию `bridge`, `host`, `none`).
- `docker network create <имя>` — своя изолированная сеть. Контейнеры в ней видят друг друга **по имени** через встроенный DNS, а снаружи до них не добраться, пока порты не опубликованы. Это базовая практика безопасности.

### 11.4. Типы сетей (`--network <тип>`)
| Тип | Как работает | Когда использовать |
|-----|--------------|--------------------|
| **bridge** (по умолчанию) | Виртуальный свитч на хосте, у контейнера свой внутренний IP (например, `172.17.0.2`). Наружу только через `-p`, трафик идёт через NAT | Основной режим изоляции приложений |
| **host** | Нет сетевой изоляции: контейнер использует сетевой стек хоста, `-p` не нужен | Максимальная скорость без накладных расходов NAT (тяжёлые БД, сбор логов) |
| **none** | Только `lo`, ни сети, ни интернета | Обработка секретов: код не сможет ничего отправить наружу |
| **overlay** | Туннель между контейнерами на разных машинах (Swarm/Kubernetes) | Кластеры |
| **macvlan** | Контейнер получает собственный MAC и IP от роутера, выглядит как отдельный компьютер | Интеграция с физической сетью |

### 11.5. Dockerfile
Файл называется строго `Dockerfile` (без расширения). Каждая инструкция `FROM`/`RUN`/`COPY` создаёт неизменяемый **слой**; неизменяемые слои кэшируются, поэтому порядок инструкций влияет на скорость сборки.

**Инструкции сборки**
- `FROM python:3.10-slim` — базовый образ (первая строка; фиксируй версию).
- `RUN apt-get update && apt-get install -y htop` — команда **при сборке**.
- `COPY ./app.py /app/` — копировать файлы с хоста в образ. `ADD` умеет ещё скачивать по URL и распаковывать архивы, но для обычного копирования используй `COPY`.
- `WORKDIR /app` — аналог `cd` для следующих инструкций.
- `ENV APP_ENV=production` — переменная, доступная и в запущенном контейнере.
- `ARG VERSION=1.0` — переменная **только на время сборки**.
- `EXPOSE 8080` — документация порта; сама порт **не** открывает, нужен `-p`.
- `USER devops` — запуск не от root: при взломе приложения злоумышленник не получит root.

**Инструкции запуска** (выполняются при старте контейнера)
- `CMD ["python", "main.py"]` — команда по умолчанию, **легко переопределяется** в `docker run`.
- `ENTRYPOINT ["nginx", "-g", "daemon off;"]` — фиксированная точка входа (переопределить можно только через `--entrypoint`).
- Используй **exec-форму** (`["…", "…"]`, а не строку): тогда процесс становится PID 1 и получает сигналы (`SIGTERM`) напрямую. Если процесс не обрабатывает сигналы, добавляй `init: true` / `--init`.

**Практики**
- Порядок слоёв: сначала зависимости (`COPY package*.json` + `npm ci`), потом исходники. Тогда кэш переиспользуется.
- **Multi-stage build**: тяжёлый этап сборки (Node, компилятор) отдельно, в финальный образ копируются только артефакты (`COPY --from=build /app/dist ...`).
- `.dockerignore`: исключить `node_modules`, `.env`, `.git`, артефакты сборки.
- Не клади секреты в образ (`ENV`, `COPY .env`): передавай их при запуске.

### 11.6. Docker Compose (v2: `docker compose`)
Описывает многоконтейнерное приложение в `docker-compose.yml`: сервисы, сети, тома, переменные.

- `docker compose up -d --build` — собрать и запустить в фоне.
- `docker compose ps` — состояние (смотри `healthy` у сервисов с healthcheck).
- `docker compose logs -f <сервис>` — живые логи.
- `docker compose exec <сервис> sh` — зайти внутрь.
- `docker compose config` — итоговый файл после подстановки переменных (удобно для отладки).
- `docker compose down` — остановить и удалить контейнеры, данные в именованных томах сохраняются.
- `docker compose down -v` — то же **и удалить тома** (данные пропадут).

Что важно в `docker-compose.yml`:
- `depends_on` с `condition: service_healthy` — порядок старта по готовности, а не просто по запуску.
- `healthcheck` — проверка здоровья сервиса. В `test` знак `$` экранируется как `$$`, чтобы переменную подставил shell контейнера, а не Compose.
- `volumes` (именованные тома) — данные переживают пересоздание контейнеров.
- `restart: unless-stopped` — автоперезапуск.
- Секреты через `.env` (в `.gitignore`) плюс `.env.example` как шаблон в репозитории.
- Наружу публикуй только то, что нужно (обычно один входной сервис).


### 11.7. Healthcheck и порядок запуска

Healthcheck периодически выполняет команду внутри контейнера. Код выхода `0` значит «здоров», иначе «нездоров».

Состояния: `starting` (идёт `start_period` или ещё не было проверок), `healthy`, `unhealthy` (подряд провалено `retries` проверок).

```yaml
services:
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 5s        # как часто проверять
      timeout: 3s         # сколько ждать ответ одной проверки
      retries: 5          # сколько неудач подряд до unhealthy
      start_period: 10s   # время на запуск: неудачи в этот период не считаются

  app:
    build: ./app
    depends_on:
      db:
        condition: service_healthy     # стартовать только когда db healthy
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:5000/health', timeout=3)"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 10s
```

- `CMD` запускает программу напрямую, `CMD-SHELL` через shell (нужен для `|`, `||`, переменных).
- В `test` знак `$` экранируется как `$$`, чтобы переменную подставил shell контейнера, а не Compose.
- В `slim`-образах Python нет `curl`, поэтому проверяют через `python -c`. В Alpine есть `wget` из busybox: `wget -qO- http://127.0.0.1:3000/health > /dev/null || exit 1`.
- В адресе healthcheck пиши `127.0.0.1`, а не `localhost`: `localhost` может резолвиться в IPv6 (`::1`), а приложение слушает только IPv4.
- `docker compose up -d --wait` ждёт, пока сервисы с healthcheck станут `healthy`, и завершается с ошибкой, если один из них `unhealthy`. Сервис без healthcheck считается готовым, как только запущен.

**Если контейнер `unhealthy`, сначала читай результаты проверок:**
```bash
docker inspect --format '{{json .State.Health}}' <контейнер>
```
В поле `Output` будет текст ошибки команды проверки (например, `SyntaxError` в Python-однострочнике или `curl: not found`). Это быстрее, чем гадать по логам.

### 11.8. Hardening контейнеров в Compose

```yaml
services:
  api:
    build: ./api
    init: true                       # PID 1 пробрасывает сигналы и убирает зомби
    user: "1000:1000"                # не root (или USER в Dockerfile)
    read_only: true                  # корневая ФС только для чтения
    tmpfs:
      - /tmp                         # место для временных файлов
    cap_drop: [ALL]                  # убрать все Linux capabilities
    security_opt:
      - no-new-privileges:true       # запрет повышения привилегий через setuid
    mem_limit: 256m
    cpus: 0.5
    logging:
      driver: json-file
      options:
        max-size: "10m"              # ротация логов, чтобы не забить диск
        max-file: "3"
    networks: [backend]

networks:
  backend:
    internal: true                   # (по желанию) сеть без доступа наружу
```

- **Сегментация сетей:** разные сети для разных связок (`edge`: frontend + api, `backend`: api + БД). Тогда фронтенд физически не видит базу.
- **Порты:** публикуй только входной сервис, на loopback: `"127.0.0.1:8081:8080"`. Docker обходит UFW (см. раздел 10), поэтому наружу выставляй через reverse proxy.

**Проверка hardening:**
```bash
docker compose top                                   # пользователи процессов, root быть не должно
docker compose exec api id -u                        # не 0
docker compose exec api touch /app/test.txt          # Read-only file system (ожидаемо)
docker compose exec api touch /tmp/test.txt          # работает благодаря tmpfs
docker compose exec frontend getent hosts redis      # не резолвится (нет общей сети)
docker stats --no-stream                             # память и CPU против лимитов
```

**Типичные ошибки после hardening:**
| Симптом | Причина | Решение |
|---------|---------|---------|
| `Read-only file system` в логах | сервис пишет не в volume и не в tmpfs | добавить путь в `tmpfs` |
| `Operation not permitted` сразу после старта | нужна capability, убранная `cap_drop: [ALL]` | вернуть только нужную через `cap_add` |
| Redis не стартует, `permission denied` на `/data` | volume создан с другим владельцем | `docker compose down -v` (данные удалятся) |

### 11.9. Безопасность образов

- **Trivy** сканирует образ на известные уязвимости (CVE):
  ```bash
  trivy image --severity HIGH,CRITICAL --ignore-unfixed myimage:tag
  ```
  `--ignore-unfixed` скрывает уязвимости, для которых исправления ещё нет.
- **Как читать таблицу:** `Library` (пакет), `Vulnerability` (номер CVE), `Severity`, `Installed Version` и `Fixed Version`. Суффикс `-r0` у версий означает пакет Alpine (`apk`): значит, проблема в базовом образе, а не в твоём коде.
- **Порядок исправления:**
  1. Пересобрать на свежем базовом образе (`docker build --pull --no-cache`).
  2. Если база ещё не обновилась, обновить пакеты в самом образе:
     ```dockerfile
     FROM nginxinc/nginx-unprivileged:<версия>-alpine
     USER root
     # hadolint ignore=DL3017
     RUN apk upgrade --no-cache
     USER nginx
     ```
     Пользователь переключается на root только на время установки и возвращается обратно: итоговый контейнер не должен работать от root. Комментарий `hadolint ignore=DL3017` нужен, потому что линтер не любит `apk upgrade` (но здесь это осознанный выбор).
  3. Поднять версию базового образа.
  4. Только в крайнем случае `.trivyignore` с CVE и **обязательным комментарием**, почему уязвимость неприменима.
- **hadolint** проверяет Dockerfile по best practices (`hadolint Dockerfile`). Отключить правило точечно: комментарий `# hadolint ignore=DLxxxx` строкой выше.
- **Версии базовых образов фиксируй** (`node:20-alpine`, `postgres:16`, не `latest`). Для повторяемости ещё надёжнее закрепить по digest (`image@sha256:...`). Обновлять версии удобно через Dependabot.

### 11.10. Сборка: кэш и сеть

- Слои кэшируются: инструкция пересобирается, только если изменилась она сама или любая выше. Поэтому сначала зависимости (`COPY package*.json` + `npm ci` или `COPY requirements.txt` + `pip install`), потом исходный код.
- `docker build --no-cache` — собрать без кэша, `--pull` — заново скачать базовый образ.
- `docker build --network=host` — собрать, используя сеть хоста. Помогает, если в WSL сборка не может разрешить DNS (ошибки загрузки пакетов во время `RUN`).
- `docker compose build` и `docker compose up --build` используют те же слои.

### 11.11. Диагностика контейнера

| Симптом | Куда смотреть |
|---------|---------------|
| Контейнер сразу `Exited` | `docker compose ps -a`, затем `docker compose logs <сервис>`, там причина и код выхода |
| `unhealthy` | `docker inspect --format '{{json .State.Health}}' <контейнер>`, поле `Output` |
| `host not found in upstream "api"` (Nginx) | имя в `proxy_pass` не совпадает с именем сервиса Compose, или сервисы не в общей сети |
| `502 Bad Gateway` | бэкенд не работает: `docker compose logs api` |
| Приложение не открывается снаружи | слушает `127.0.0.1` внутри контейнера, а нужно `0.0.0.0`; не опубликован порт |
| Падает `docker compose config` | чаще всего YAML: съехали отступы (только пробелы, не табы) |
| Остались «висящие» тома, образы | `docker system df`, `docker system prune` (осторожно) |

Ошибки `docker compose config`:
- `additional properties 'xxx' not allowed`: ключ стоит не на своём уровне (например, `healthcheck` оказался внутри `depends_on`). Ключи сервиса (`image`, `build`, `depends_on`, `healthcheck`, `ports`) стоят на одном уровне отступа.
- `mapping key "xxx" already defined`: один ключ дважды в одном блоке, обычно от того, что блоки двух сервисов склеились.
- `variable is not set` / `REDIS_PASSWORD is not set`: в `.env` нет переменной, а в Compose стоит `${VAR:?...}`.

## 12. CI/CD (GitHub Actions)

### 12.1. Основные понятия

- **CI** (Continuous Integration): каждое изменение автоматически проверяется (линт, сборка, тесты, сканирование). Красный результат блокирует слияние.
- **CD** (Continuous Delivery/Deployment): проверенная версия автоматически доставляется на сервер.
- **Путь деплоя:** `git push` → CI → образ в реестре → сервер скачивает образ → запуск. Откат: запустить предыдущий образ по тегу с хэшем коммита.
- **Pipeline** (пайплайн): набор автоматических шагов. Читаем его сверху вниз.

### 12.2. Git-процесс под CI

Любое изменение идёт так: **ветка → коммит → pull request → зелёный CI → merge**.

```bash
git switch main && git pull                  # свежий main
git switch -c ci/my-change                   # новая ветка
# ... правки ...
git add <файлы>
git commit -m "ci: описание"                 # Conventional Commits
git push -u origin ci/my-change              # -u запоминает связь с удалённой веткой
# открыть Pull Request на GitHub, дождаться зелёных проверок, смержить
```

**После merge:**
```bash
git switch main
git pull
git branch -d ci/my-change                   # удалить локальную ветку
git push origin --delete ci/my-change        # удалить удалённую (или кнопка Delete branch)
git fetch --prune                            # убрать устаревшие ссылки на удалённые ветки
```
- `git branch -d` удаляет только полностью слитую ветку; `-D` удаляет принудительно (осторожно).
- Если `-d` ругается «not fully merged», сначала синхронизируйся с `origin/main`.

**Конфликт слияния** (в файле появились маркеры):
```
<<<<<<< HEAD (текущая ветка)
твоя версия
=======
версия из другой ветки
>>>>>>> main
```
Оставь нужный итог (часто комбинацию обеих версий), **удали все три маркера**, затем `git add <файл>` и `git commit`. Маркеры в файле ломают YAML и скрипты.

**`git pull` пишет «divergent branches»:** история локальная и удалённая разошлась (у каждой есть свои коммиты). Варианты:
```bash
git log --oneline --graph --all -n 10         # посмотреть, что где
git pull --rebase                             # переложить свои коммиты поверх удалённых (линейная история)
git config --global pull.rebase true          # сделать rebase режимом по умолчанию
```
Если локальный коммит не нужен (например, его уже слили иначе на GitHub): сначала резервная ветка, потом сброс:
```bash
git branch backup-main
git reset --hard origin/main                  # опасно: отбрасывает локальные коммиты и правки
```

**Защита `main`** (Settings → Rules → Rulesets): обязательный pull request, запрет force push и удаления ветки, обязательные проверки (`Require status checks`). Ловушка: если у workflow есть фильтр `paths`, то на PR без изменений в этих папках проверка не запускается и обязательная проверка висит как «Expected» навсегда. Обязательными делай проверки без `paths` (например, сканирование секретов). В приватных репозиториях на бесплатном тарифе rulesets недоступны.

### 12.3. Устройство GitHub Actions

Workflow лежит в `.github/workflows/*.yml` (расширение `.yml` или `.yaml`, строго эта папка).

| Термин | Что это |
|--------|---------|
| **Workflow** | один YAML-файл с автоматизацией |
| **Event** (`on:`) | что запускает: `push`, `pull_request`, `workflow_dispatch`, `schedule` |
| **Job** | набор шагов на одном раннере; jobs по умолчанию идут **параллельно** |
| **Runner** | виртуальная машина (`ubuntu-latest`), чистая на каждый запуск |
| **Step** | один шаг: `run:` (команда shell) или `uses:` (готовый экшен) |
| **Action** | готовый переиспользуемый блок (`actions/checkout`, `docker/build-push-action`) |

```yaml
name: my-ci

on:
  push:
    branches: [main]
    paths:                              # запускать, только если менялось это
      - "myapp/**"
      - ".github/workflows/my-ci.yml"
  pull_request:
    paths:
      - "myapp/**"
      - ".github/workflows/my-ci.yml"
  workflow_dispatch:                    # кнопка ручного запуска
  # schedule:
  #   - cron: "0 5 * * 1"               # по расписанию (UTC)

permissions:
  contents: read                        # права токена по минимуму

concurrency:                            # новый пуш отменяет прошлый запуск в той же ветке
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 10                 # защита от зависаний
    defaults:
      run:
        working-directory: myapp        # только для шагов run:, не для uses:
    steps:
      - uses: actions/checkout@v7       # скачать код
      - name: Validate
        run: docker compose config > /dev/null
      - name: Show logs
        if: failure()                   # только если что-то упало выше
        run: docker compose logs
      - name: Cleanup
        if: always()                    # выполнять в любом случае
        run: docker compose down -v

  scan:
    needs: build                        # запуститься после успеха job build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
```

Полезное:
- `with:` передаёт параметры экшену; `env:` задаёт переменные окружения; `${{ secrets.NAME }}` читает секрет; `${{ github.sha }}` хэш коммита; `${{ github.actor }}` кто запустил.
- Условие для публикации только на `main`: `if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'`.
- **Один PR запускает все workflow, чьи триггеры сработали**, поэтому нужны `paths`, иначе на любой PR запустятся все проекты.
- **`schedule`** работает только из файла в главной ветке; время в UTC. В публичных репозиториях GitHub отключает расписание после 60 дней без активности (включается кнопкой во вкладке Actions).
- **Matrix** запускает job для каждого значения:
  ```yaml
  strategy:
    fail-fast: false                    # не отменять остальные при падении одного
    matrix:
      include:
        - name: guestbook-api
          context: guestbook-new/api
        - name: todo-app
          context: archive_projects/docker-compose2/app
  # дальше ${{ matrix.name }} и ${{ matrix.context }}
  ```
- **`needs`** задаёт порядок: если упал нужный job, зависимый пропускается.

### 12.4. Типовой пайплайн для Docker-проекта

1. **Lint** Dockerfile (hadolint).
2. **Validate** Compose (`docker compose config`).
3. **Build** (`docker compose build`).
4. **Smoke test**: поднять стек и проверить, что он реально работает.
5. **Scan** образа (Trivy), падение на HIGH и CRITICAL с исправлением.
6. **Publish** образов в реестр (только на `main`, после всех проверок).

В CI вместо настоящего `.env` берём шаблон: `cp .env.example .env` (в нём тестовые значения, реальных секретов нет).

**Smoke test** на `curl`:
```bash
docker compose up -d --wait
curl -fsS --retry 10 --retry-connrefused --retry-delay 2 --max-time 5 http://127.0.0.1:5000/health
# запись и чтение: проверка, что работает БД, а не просто отвечает приложение
curl -fsS --max-time 5 -X POST http://127.0.0.1:5000/todos \
  -H "Content-Type: application/json" -d '{"title": "ci"}'
curl -fsS --max-time 5 http://127.0.0.1:5000/todos | grep -q '"ci"'
```

| Флаг curl | Что делает |
|-----------|------------|
| `-f` | вернуть ошибку на ответ 4xx/5xx (без него `500` считался бы успехом) |
| `-s` | не печатать таблицу прогресса |
| `-S` | но показывать текст ошибки, если она есть |
| `--retry N` | повторить до N раз при временных ошибках |
| `--retry-connrefused` | считать «connection refused» временной ошибкой (сервис ещё стартует) |
| `--retry-delay N` | пауза между повторами в секундах |
| `--max-time N` | максимум N секунд на один запрос (чтобы не висеть) |
| `-X POST`, `-H`, `-d` | метод, заголовок, тело запроса |

**Важно: длинные флаги пишутся с двумя дефисами.** `-retry-delay 2` curl разбирает как набор коротких флагов, а `2` принимает за адрес (отсюда бесконечные строки с нулями в логе и зависший шаг).

### 12.5. Публикация образов в GHCR

```yaml
publish:
  needs: [lint-and-build, image-scan]
  if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'
  runs-on: ubuntu-latest
  permissions:
    contents: read
    packages: write                     # право на push в реестр, только этому job
  steps:
    - uses: actions/checkout@v7
    - uses: docker/setup-buildx-action@v4   # сборщик Buildx (нужен для кэша)
    - uses: docker/login-action@v4
      with:
        registry: ghcr.io
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}   # встроенный краткоживущий токен
    - uses: docker/build-push-action@v7
      with:
        context: guestbook-new/api
        push: true
        tags: |
          ghcr.io/${{ github.repository_owner }}/guestbook-api:latest
          ghcr.io/${{ github.repository_owner }}/guestbook-api:${{ github.sha }}
        cache-from: type=gha,scope=api
        cache-to: type=gha,mode=max,scope=api
```

- Тег `latest` удобен, тег с `github.sha` нужен для **точного отката** и воспроизводимости.
- Адрес реестра `ghcr.io` (опечатка `ghrc.io` даёт `denied`). Имя образа должно быть в нижнем регистре.
- На сервере вход в GHCR: токен (PAT) с правом `read:packages`, `docker login ghcr.io -u <user>`.
- **Параметры `build-push-action`:** `context` (папка сборки, как `build:` в Compose), `push: true` (отправить в реестр), `load: true` (загрузить собранный образ в локальный Docker раннера, нужно для сканирования; Buildx по умолчанию не кладёт образ в `docker images`), `tags` (имена), `cache-from` / `cache-to` (кэш слоёв в хранилище GitHub Actions; `scope` разделяет кэш разных образов, `mode=max` сохраняет и промежуточные стадии).

### 12.6. Безопасность в CI

- **Секреты:** никогда не в Git. Для CI используются GitHub Secrets (`${{ secrets.NAME }}`) и тестовые значения из `.env.example`. Если секрет попал в историю, удаления файла недостаточно: ключ нужно **перевыпустить**.
- **Минимальные права токена:** `permissions: contents: read` на уровне workflow; расширенные права (`packages: write`) только в том job, которому они нужны. Указанное в `permissions` ограничивает всё остальное до `none`.
- **Сканирование секретов:** `gitleaks` с `fetch-depth: 0` (нужна вся история, а не последний коммит) на каждый пуш и PR.
- **Закрепление экшенов по хэшу коммита** (`uses: owner/action@<40 символов>  # v1.2.3`): тег можно переместить на другой код, хэш нельзя. Минимум для экшенов безопасности (Trivy).
- **Dependabot** (`.github/dependabot.yml`) раз в неделю открывает PR с обновлениями:
  ```yaml
  version: 2
  updates:
    - package-ecosystem: "github-actions"
      directory: "/"
      schedule:
        interval: "weekly"
    - package-ecosystem: "docker"            # FROM в Dockerfile
      directory: "/myapp/api"
      schedule:
        interval: "weekly"
    - package-ecosystem: "docker-compose"    # image: в compose-файле
      directory: "/myapp"
      schedule:
        interval: "weekly"
    - package-ecosystem: "npm"               # или "pip" для requirements.txt
      directory: "/myapp/api"
      schedule:
        interval: "weekly"
  ```
  Каждый `directory` должен существовать, иначе Dependabot выдаст ошибку.
- **Регулярное сканирование:** новые уязвимости находят и без изменений в коде, поэтому Trivy запускают ещё и по `schedule`.

### 12.7. Как читать упавший пайплайн

1. Найти **первый красный шаг** (последующие часто серые или красные из-за него).
2. Прочитать **конец лога** этого шага: там причина.
3. Воспроизвести локально теми же командами (`docker compose config`, `docker compose up -d --build --wait`).

**Каталог ошибок:**

| Симптом | Причина | Решение |
|---------|---------|---------|
| `Set up job` красный, `unable to find version` | неверный тег экшена (нет `v`, версии не существует) | сверить тег на странице экшена |
| `docker compose config > dev/null` падает | потерян `/` в `/dev/null` | исправить путь |
| `REDIS_PASSWORD is not set` | пустое значение в `.env.example` | задать тестовое значение |
| `denied` при push в GHCR | опечатка `ghrc.io` вместо `ghcr.io`, нет `packages: write` | исправить адрес / права |
| `Unexpected value 'worklflow_dispatch'` | опечатка в ключе workflow | исправить ключ |
| `invalid --security-opt` | опечатка `no-new-priveledges` | `no-new-privileges` |
| Шаг с `curl` висит, в логе нули и растущее время | `-retry-delay` с одним дефисом, нет `--max-time` | `--retry-delay`, добавить `--max-time`, `timeout-minutes` |
| `container ... is unhealthy` | ошибка в самой команде healthcheck или приложение не стартует | `docker inspect ... .State.Health`, поле `Output` |
| `additional properties 'xxx' not allowed` / `mapping key ... already defined` | съехали отступы в YAML | выровнять уровни, только пробелы, `docker compose config` локально |
| `image-scan` красный, таблица Trivy | в образе пакеты с известными уязвимостями, исправление уже вышло | пересобрать на свежей базе или `apk upgrade`, см. 11.9 |
| Конфликт слияния в редакторе | в `main` и в ветке изменена одна и та же строка | оставить итог, удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>` |
| `Invalid workflow file` | ошибка YAML (отступы, опечатка в ключе) | проверить отступы и имена ключей |
| На PR `Checks 0` и крутится «Checking for the ability to merge» | задержка на стороне GitHub | подождать 1-2 минуты, Ctrl+F5; проверить вкладку Actions |
| Из одного PR запустилось несколько workflow | сработали триггеры нескольких файлов, нет `paths` | добавить `paths` в `pull_request`, `concurrency` |
| Обязательная проверка висит «Expected» | workflow не запустился из-за `paths` | делать обязательными только проверки без `paths` |

### 12.8. Основы CD (дальнейший план)

- Для деплоя создаётся **отдельный SSH-ключ** (не личный) и кладётся в GitHub Secrets, а публичная часть на сервер.
- Деплой-workflow по успешному CI заходит на сервер и выполняет `docker compose pull && docker compose up -d`.
- **Environment `production`** с ручным подтверждением защищает от случайного деплоя.
- **Откат:** развернуть предыдущий образ по тегу с хэшем коммита (поэтому образы публикуются с `${{ github.sha }}`).
- Сервер за reverse proxy (Caddy) с доменом и HTTPS; порт приложения привязан к `127.0.0.1`.

### 12.9. Ветки, Dependabot и порядок работы

**Именование веток:** `тип/короткое-описание`, строчные буквы, слова через дефис, без пробелов и кириллицы. Тип совпадает с типом коммита.

| Задача | Имя ветки |
|--------|-----------|
| новая возможность | `feat/frontend-healthcheck` |
| исправление | `fix/api-graceful-shutdown` |
| документация | `docs/notes-ci-docker` |
| рутина, зависимости, версии | `chore/pin-base-images` |
| CI | `ci/todo-image-scan` |

**Одна задача означает одну ветку и один PR.** Причины: защита `main` всё равно требует PR; при красном CI понятно, какая правка виновата; каждую правку можно откатить отдельно. Мелкие связанные изменения (healthcheck и `internal: true` для сети) можно держать в одной ветке. Новую ветку, зависящую от предыдущей правки, начинают после merge того PR.

**Pull request от Dependabot:**
- Ветки `dependabot/...` не удаляют вручную: каждая принадлежит открытому PR. Правильно работать через сам PR.
- Порядок оценки: тип обновления (patch, minor, **major**), зелёный ли CI, release notes в тексте PR.
- Мажорные версии осторожно: может ломаться API (Express 4 → 5, Redis-клиент 4 → 5+). Мажорная версия БД (Postgres 16 → 18) несовместима с существующим томом без миграции (`pg_dump` и восстановление или `pg_upgrade`).
- Для Node выбирай **LTS** (чётные версии); нечётные («Current») живут недолго.
- Команды Dependabot в комментарии к PR:
  ```
  @dependabot rebase                       # пересобрать PR на свежем main
  @dependabot recreate                     # пересоздать PR с нуля
  @dependabot close                        # закрыть PR
  @dependabot ignore this major version    # закрыть и не предлагать эту мажорную версию
  @dependabot ignore this dependency       # закрыть и не предлагать эту зависимость
  ```
  При `ignore ...` Dependabot сам удалит ветку.
- Чтобы ветки не копились: **Settings → General → Pull Requests → Automatically delete head branches**.
- Ограничить поток PR в `dependabot.yml`:
  ```yaml
      open-pull-requests-limit: 3
      groups:
        python-deps:
          patterns: ["*"]          # мелкие обновления одним PR
  ```

## 13. Вопросы для собеседований: Docker и CI

Краткие эталонные ответы. Учить не наизусть, а пересказывать своими словами, добавляя пример из своих проектов.

### Docker

**1. Контейнер и виртуальная машина: чем отличаются, что общего?**
ВМ эмулирует железо через гипервизор и запускает **своё ядро ОС**: тяжёлая, стартует минуты, изоляция сильнее. Контейнер это изолированный процесс на **ядре хоста**: изоляция через namespaces (что процесс видит), лимиты через cgroups (сколько ресурсов может взять). Он весит мегабайты и стартует за секунды. Общее: оба изолируют приложения, запускаются из образа/шаблона, переносимы, имеют свою сеть и файловую систему. На Windows Linux-контейнеры работают в лёгкой Linux-ВМ (WSL2).

**2. Образ и контейнер. Что с данными после `docker rm`?**
Образ это неизменяемый шаблон из слоёв только для чтения. Контейнер это запущенный экземпляр с тонким слоем для записи сверху. После `docker rm` слой удаляется вместе с данными. Чтобы данные пережили контейнер, их выносят в именованный том или bind mount (пример: том `redis-data` в Guestbook; `down` его сохраняет, `down -v` удаляет).

**3. Как работает кэш слоёв? Почему сначала копируют `package.json`?**
Каждая инструкция это слой; если инструкция и её входные файлы не изменились, слой берётся из кэша. Если слой изменился, все последующие пересобираются. Код меняется часто, зависимости редко, поэтому сначала копируют файл зависимостей и ставят их, а исходники после: тяжёлый шаг установки остаётся в кэше. Это про скорость пересборки, а не про размер образа.

**4. `CMD` и `ENTRYPOINT`; зачем exec-форма?**
`RUN` выполняется при сборке, `CMD` и `ENTRYPOINT` задают, что запускать при старте. `CMD` это команда по умолчанию, её можно заменить в `docker run`; `ENTRYPOINT` фиксирует программу, а переданное становится её аргументами. Exec-форма (`["python", "app.py"]`) делает приложение PID 1, и оно получает `SIGTERM` при `docker stop`. В shell-форме PID 1 это shell, сигнал не доходит, и контейнер убивается через 10 секунд (код 137).

**5. `EXPOSE` и `-p`; как контейнеры находят друг друга?**
`EXPOSE` только документирует порт. `-p 8080:80` публикует: порт 8080 хоста перенаправляется на порт 80 контейнера. В Compose создаётся сеть со встроенным DNS, который превращает имя сервиса в IP, поэтому Nginx обращается к `http://api:3000`. Наружу публикуется только frontend, `api` и Redis доступны лишь внутри сети (у меня две сети, `edge` и `backend`, так что frontend не видит Redis).

**6. Почему одного `depends_on` мало?**
Он ждёт только запуска контейнера, а не готовности сервиса: Postgres после старта ещё инициализируется, и приложение может упасть с `connection refused`. Добавляют `healthcheck` у базы (`pg_isready`) и в приложении `depends_on` с `condition: service_healthy`. Проверка: `docker compose ps` (статус `healthy`), `docker compose up -d --wait`, `docker inspect --format '{{json .State.Health}}' <контейнер>`.

**7. Контейнер упал или `unhealthy`. Что делаешь?**
Смотрю статус и код выхода (`docker compose ps -a`), читаю логи (`docker compose logs <сервис>`). При `unhealthy` логи могут быть чистыми, а сломана сама проверка, поэтому читаю `docker inspect ... .State.Health` (поле `Output`). Дальше сверяю конфиг (`docker compose config`), переменные окружения, порты, адрес прослушивания (`0.0.0.0`), сеть и DNS (`getent hosts`), права на тома. При необходимости захожу внутрь (`docker compose exec <сервис> sh`) и воспроизвожу проблему вручную.

### CI и GitHub Actions

**8. CI и CD; Continuous Delivery и Continuous Deployment.**
CI это автоматическая проверка каждого изменения (линт, сборка, тесты, сканирование), цель в быстрой обратной связи об ошибках. Continuous Delivery: каждая проверенная версия готова к выкатке, но выкат запускается человеком (кнопка, подтверждение). Continuous Deployment: после зелёных проверок выкат на прод происходит автоматически, без ручного шага.

**9. Из чего состоит workflow в GitHub Actions?**
Workflow это YAML-файл в `.github/workflows/`. Event (`on:`) запускает его (`push`, `pull_request`, `schedule`, `workflow_dispatch`). Внутри jobs, каждый выполняется на своём runner (чистая виртуальная машина) и состоит из steps: `run:` (команда) или `uses:` (готовый action). Jobs идут **параллельно** по умолчанию; порядок задаётся через `needs:` (в моём пайплайне `image-scan` ждёт `lint-and-build`).

**10. Где хранить пароли и токены для CI?**
В GitHub Secrets (`${{ secrets.NAME }}`), в логах они маскируются. В репозиторий их класть нельзя: Git хранит историю навсегда, и удаление файла не помогает. Если секрет утёк, его нужно **перевыпустить**. Защита: `.env` в `.gitignore`, шаблон `.env.example` с тестовыми значениями, `gitleaks` по всей истории, push protection.

**11. Что такое `GITHUB_TOKEN` и принцип минимальных прав?**
Это токен, который GitHub автоматически создаёт на время запуска workflow. Его права ограничивают блоком `permissions`. Принцип: давать только необходимое. У меня на уровне workflow `contents: read`, а `packages: write` выдан только job публикации образов в GHCR.

**12. Пайплайн покраснел. С чего начинаешь?**
Нахожу **первый красный шаг** (остальные красные часто следствие), читаю конец его лога. Типичные причины: опечатка в YAML или флаге, неверный тег action, пустой секрет, уязвимость в Trivy, упавший smoke-тест. Воспроизвожу локально теми же командами. Перезапуск (`Re-run failed jobs`) уместен только для сбоев инфраструктуры, а не как способ «починить».

**13. Что такое smoke-тест и чем отличается от юнит-теста? Зачем `--retry`?**
Smoke-тест это быстрая проверка уже собранной и запущенной системы: поднимается ли она и работают ли ключевые функции (`/health`, запись и чтение через БД). Юнит-тест проверяет отдельную функцию изолированно, без окружения. `--retry` и `--retry-connrefused` нужны, потому что сервис стартует не мгновенно; `--max-time` не даёт одной попытке повиснуть.

**14. Новая версия сломана после деплоя. Как откатиться?**
Образы публикуются с тегом из хэша коммита (`guestbook-api:<sha>`), поэтому на сервере достаточно поднять предыдущий тег. Заранее должно быть готово: в compose тег задан переменной (`image: ghcr.io/<owner>/guestbook-api:${TAG:-latest}`), известен предыдущий рабочий `sha`, старые образы остаются в реестре, миграции данных обратимы. Команда: `TAG=<prev-sha> docker compose pull && TAG=<prev-sha> docker compose up -d`. Ручное подтверждение в Environment `production` и smoke-тест после деплоя уменьшают риск.
